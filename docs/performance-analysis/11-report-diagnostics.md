# Диагностика отчёта о производительности

## Что сейчас формируется

В JSON-отчёт попадают **только подтверждённые расчётом риски насыщения**
`capacity_saturation`: коэффициент загрузки узла достигает порога 98%.
Это ранний предупредительный порог, а не математическое доказательство отказа.

Числовые метрики хранятся непосредственно в `nodes`, а не дублируются
сообщениями «есть запас». Ограничения модели, невычисленные p95/p99 и конечные
буферы также не создают текстовых findings: отсутствующие оценки остаются
`null`. Общая полнота доступных вычислений по-прежнему фиксируется в `status`.

Для совместимости со старыми JSON версии 1.0 enum
`PerformanceFindingCode` продолжает принимать исторические коды
(`capacity_headroom`, `workload_missing`, `metric_unavailable`,
`unsupported_model`, `bounded_queue_unmodeled`,
`latency_not_evaluated`). Новые отчёты их **не генерируют**.
Новая версия схемы не требуется, потому что набор допустимых полей и типов
не меняется.

## Детерминированность

- Узлы упорядочены по `node_identifier` независимо от порядка C4.
- Подтверждённые перегрузки упорядочены по идентификатору узла.
- Рекомендация по масштабированию не обещает конкретного выигрыша.
- Средние задержки не объявляются проверкой p95/p99.
- PDF продолжает показывать только рассчитанные числа и перегрузку.
