# Диагностика отчёта о производительности: этап 11

## Зачем нужны findings

Пользователь видит утилизацию и задержку, но не всегда понимает их смысл.
**Finding** — детерминированный вывод по метрикам и допущениям. Это не
решение LLM, не результаты стресс-теста и не гарантия SLA.

Каждый finding содержит машинный код, уровень важности, список затронутых
узлов, заголовок, объяснение и необязательную рекомендацию. Числовые тесты
должны проверять коды, значения и узлы, **не полный русский текст**.

| Код | Уровень | Значение |
| --- | --- | --- |
| \`capacity_saturation\` | error | Загрузка >= 98%; это раннее предупреждение, а не математическая граница стабильности |
| \`capacity_headroom\` | info | Загрузка < 98% в рамках модели; не обещает запас мощности реальной системы |
| \`workload_missing\` | warning | Нет профиля RPS; нельзя заменять его отсутствием нагрузки |
| \`unsupported_model\` | warning | Альтернативные маршруты считаются равновероятными без доказанных весов |
| \`metric_unavailable\` | warning | Число каналов неизвестно, неустойчиво или оценка недопустима; числовое поле null |
| \`bounded_queue_unmodeled\` | warning | Конечная очередь не даёт честной вероятности потерь по формулам бесконечного буфера |
| \`latency_not_evaluated\` | warning | Среднее время ответа не проверяет p95/p99 |

## Что стало детерминированным

- Узловые метрики выдаются по \`node_identifier\` независимо от порядка исходных узлов.
- Findings сортируются по приоритету error, затем warning, затем info,
  далее по коду и затронутым узлам.
- Список \`affected_node_identifiers\` сортируется по имени.
- При равной сумме средних задержек синхронных путей выбирается стабильный
  путь по идентификаторам, а не случайный порядок рёбер.
- Для нескольких альтернативных database fallback после cache miss вновь
  показывается допущение о равных долях; единственный fallback такого
  warning не вызывает.

## Примеры, проверяемые вручную

**Нагрузка ниже предела:** один канал обрабатывает 200 RPS, поступает 20 RPS:
\`ρ = 20/200 = 0.1\`. Итог: \`capacity_headroom\`, уровень info.

**Нагрузка возле предела:** максимум 100 RPS, поступает 98 RPS:
\`ρ=0.98\`. Итог: \`capacity_saturation\`, уровень error по порогу 98%.
Это ещё не математическая неустойчивость.

**Выше предела:** максимум 10 RPS, поступает 20 RPS:
\`ρ=2\`. Итог: \`capacity_saturation\` и отсутствие конечной стационарной
задержки (null с \`metric_unavailable\`). Для того же узла не должно быть
\`capacity_headroom\`.

Наличие другого предупреждения, например о конечной очереди, не обязательно
противоречит расчёту запаса: оно сообщает о другой предпосылке модели.

## Границы

Сортировка улучшает воспроизводимость JSON, но не точность математической модели.
Рекомендация по масштабированию допустима лишь при диагностированном риске,
без обещаний точного выигрыша. Текущие findings могут агрегировать несколько
причин недоступности времени; дальнейшая детализация потребует новых
типизированных кодов или понятных правил совместимости.
