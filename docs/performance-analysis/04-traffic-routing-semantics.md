# Семантика маршрутизации нагрузки

## Решение

Поле `Edge.routing_mode` задаёт, как исходящий поток узла распределяется по рёбрам:

- `alternative`: рёбра с этим режимом представляют альтернативные маршруты. Поток делится поровну между альтернативными рёбрами одного источника.
- `fan_out`: каждый запрос вызывает каждую зависимость с этим режимом, поэтому каждое ребро получает полный исходящий поток.

У источника могут одновременно быть обязательные fan-out-зависимости и набор альтернативных рёбер. Каждая fan-out-зависимость получает полный поток, а поток альтернатив делится между альтернативами. Модель не поддерживает несколько независимых групп альтернатив для одного источника.

Для старых графов без поля `routing_mode` применяется `alternative`. Это сохраняет загрузку старого JSON и прежнее поведение ветвления по умолчанию. Веса маршрутов не добавлены: в существующей модели нет источника вероятностей или долей маршрутизации.

## Пример: альтернативные маршруты

Пусть узел получает 100 запросов/с и выбирает один из двух альтернативных маршрутов. При равномерном распределении каждый маршрут получает:

\[
R_{route} = \frac{100}{2} = 50\;\text{запросов/с}
\]

Для этого оба ребра используют `routing_mode: alternative` или опускают поле. Модель не утверждает, что реальный балансировщик обязательно распределяет трафик поровну.

## Пример: fan-out

Если каждый входящий запрос вызывает две независимые зависимости, каждая получает 100 запросов/с:

\[
R_{dependency_1} = R_{dependency_2} = 100\;\text{запросов/с}
\]

Оба ребра задаются как `routing_mode: fan_out`. Суммарная нагрузка на зависимости больше исходного потока, поскольку один запрос порождает два обращения.

## Пример: обязательная зависимость и альтернатива

При исходном потоке 100 запросов/с одна обязательная fan-out-зависимость получает 100 запросов/с. Если дополнительно заданы два альтернативных ребра, они получают по 50 запросов/с. Это описывает каждый запрос, который вызывает обязательную зависимость и ровно одну из двух альтернатив.

## Cache miss path

Кэш не вызывает базу данных самостоятельно. Чтение из кэша и обращение к базе задаются
двумя синхронными исходящими рёбрами одного compute:

- `compute -> cache` получает рассчитанный для этой связи поток запросов;
- `compute -> database` представляет fallback и получает только долю промахов:
  `R_{miss} = R_{cache\_edge} \\times (1 - hit\\_rate)`;
- при hit rate 0 база получает весь поток ребра чтения кэша, при 0.8 — 20%, при 1.0 — ноль запросов.

Fallback-ребро от того же compute не считается обычным альтернативным маршрутом:
его интенсивность выводится из ребра чтения кэша. Если указано несколько синхронных
database fallback-рёбер, режим маршрутизации распределяет между ними только поток
промахов. В отчёте несколько альтернативных fallback-рёбер образуют отдельную
группу от обычных альтернативных маршрутов: равное распределение miss-трафика
вызывает диагностическое предупреждение. Одно fallback-ребро не создаёт
ложного предупреждения, а явный fan-out не трактуется как равные альтернативы. Один compute не может читать из нескольких кэшей: модель не содержит
сопоставления каждого кэша с отдельным fallback, поэтому такой граф отклоняется.
Соединение `cache -> database` запрещено: cache не является инициатором запроса.

## Реализация и проверка

- Модель: `src/domain/models/edges.py`, `src/domain/models/enums.py`.
- Расчёт RPS: `src/domain/specifications/traffic_flow.py`.
- Проверка пути промахов: `src/domain/specifications/cache_usage_validator.py`.
- Инструкции генерации: `src/infrastructure/prompts/fragments_schema.py`.
- Числовые тесты: `tests/unit/test_traffic_flow.py` и `tests/unit/test_cache_usage_validator.py`.
- Совместимость старого JSON: `tests/unit/design/test_parser.py`.

Модель ограничена равными альтернативными долями и одной группой альтернативных рёбер на источник. Весовые коэффициенты, условные ветви и несколько независимых групп маршрутизации требуют отдельного контракта, а не догадок из текстового описания ребра.
