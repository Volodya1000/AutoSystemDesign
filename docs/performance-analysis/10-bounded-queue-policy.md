# Ограниченные очереди: политика первой версии

> **Сначала:** [обозначения M/M/c/K с нуля](QUEUEING_THEORY_FOR_BEGINNERS.md).

**M/M/c/K** — расширение нотации Кендалла. Здесь `K` означает **общую
вместимость системы (обслуживаемые + ожидающие)**, а не только размер очереди.
Например, `M/M/2/5` имеет два обработчика и максимум пять заявок в системе:
две могут обслуживаться, ещё три ждать. Если все пять мест заняты, поведение
нового запроса зависит от политики отказа/блокировки.

В AutoSystemDesign сейчас задан `maximum_queue_size` — количество мест
для **ожидающих**. Простое сложение `c + maximum_queue_size` ещё не делает
реальную систему точной M/M/c/K: нужно согласовать распределения поступления
и обслуживания, FIFO и политику переполнения. Поэтому рассчитывать потери
без этих правил мы **не будем**.

## Решение

`maximum_queue_size` задаёт конечное число ожидающих запросов. Оно **не** эквивалентно количеству каналов обслуживания (`service_channels_per_replica`) или количеству одновременно находящихся в работе запросов (`maximum_concurrency`).

Точная оценка отказов и времени ожидания для ограниченной очереди зависит от как минимум модели поступления, распределения обслуживания, числа каналов и поведения при переполнении: отклонение, ожидание у клиента, backpressure или повторные попытки. Нельзя выводить процент потерь только из `maximum_queue_size`, средней длительности обработки и пикового RPS.

Поэтому в первой версии **не вводится фиктивная M/M/c/K** и не выдумывается коэффициент потерь. Вместо неё принят диагностический режим:

- Для активных узлов с конечным буфером отчёт добавляет стабильный код `bounded_queue_unmodeled`, severity `warning` и идентификаторы узлов.
- Отчёт получает статус `partial`, так как реальное поведение ограниченного буфера не проверено.
- Для `maximum_queue_size > 0` текущая аппроксимация Allen–Cunneen даёт условную оценку **неограниченной очереди**, а не фактическое время в системе с отказами. В JSON это явное ограничение сопровождается диагностикой.
- Для `maximum_queue_size = 0` при положительной нагрузке ожидание и среднее время ответа оставляются `null`. Нулевая длина очереди не означает нулевое ожидание всех поступивших запросов: часть может быть отклонена. Время обслуживания принятых запросов без модели отказов нельзя автоматически выдавать за среднее время всех обращений.
- При нулевой входящей нагрузке модель может показать нулевое ожидание без диагностики переполнения для неактивного узла.

## Границы и формулы

При \(c\) независимых каналах обслуживания и очереди длиной \(q\) простой сценарий M/M/c/K имел бы общую вместимость \(K=c+q\). Важно, что даже эта интерпретация подразумевает определённые дисциплину ожидания и политику отказа. Она **не** следует автоматически из топологической модели.

Для неограниченной очереди при пуассоновском потоке оценка задержки описана в [08-ggc-latency-approximation.md](08-ggc-latency-approximation.md). Для ограниченного буфера полученные там формулы не становятся точными от добавления `maximum_queue_size`.

### Числовой пример

Один канал со средним временем обслуживания 10 мс имеет номинальную мощность 100 запросов/с. При 20 RPS и экспоненциальном обслуживании неограниченная M/M/1 имела бы среднее ожидание 2,5 мс. При `maximum_queue_size=5` эта величина может оставаться proxy-оценкой, но реальное ожидание принятых запросов и вероятность отказа зависят от конечного буфера; отчёт помечается `partial`. При `maximum_queue_size=0` та же оценка ожидания 2,5 мс вообще неприменима и поэтому возвращается `null`.

## Реализация и проверка

- Схема кодов: `src/domain/performance_analysis/report.py`.

- Связанное обоснование: [09-queue-metrics-json-report.md](09-queue-metrics-json-report.md).

Полноценный M/M/c/K и контракты политик `reject`, `drop`, `block`, `retry` можно внедрять позже **только вместе** с моделями, проверяемыми числовыми эталонами и явными параметрами политики. В текущем JSON вероятности отказа нет.
