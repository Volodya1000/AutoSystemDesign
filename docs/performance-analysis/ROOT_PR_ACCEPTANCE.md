в одной интеграционной ветке. Ответственный PR:

  `pdf_renderer.py`, сценарии и новые integration-тесты.
- [ ] **Конфликты и регрессии разрешены на HEAD #90**, а не только на
  последнем дочернем PR. Зафиксированы SHA `master` и SHA `#90`.
- [ ] На **итоговом SHA #90** прошли все пять GitHub Actions:
  Ruff/mypy/Pylint, архитектурные импорты, поиск дублирования,
  unit-тесты, чистота репозитория и `uv.lock`.
- [ ] `uv sync --locked --all-groups` успешно устанавливает зависимости

- [ ] Никакой реальный LLM, PlantUML-сервер или интернет не требуется для

## B. Проверка математической корректности

- [ ] Одинаковые входные данные дают одинаковый JSON (порядок узлов,
  findings и выбранный путь при равных задержках).
- [ ] **M/M/1:** λ=10 RPS, μ=20 RPS, ρ=0.5, Wq=50 мс,
  W=100 мс; λ>=μ означает `unstable` и `null` вместо фиктивного времени.
- [ ] **M/M/c:** λ=10 RPS, μ=20 RPS на канал, c=2:
  вероятность ожидания 0.1, Wq≈3.33 мс, W≈53.33 мс;
  c=1 совпадает с M/M/1.
- [ ] **G/G/c:** применение Allen–Cunneen объяснено как **приближение**
  с предположением c_a²=1 (пуассоновские приходы), не как точная M/M/c.
- [ ] Нельзя автоматически приравнивать `maximum_concurrency` к количеству
  независимых каналов `service_channels_per_replica`.
- [ ] Нет противоречия `capacity_headroom` и `capacity_saturation` для
  одного узла; при перегрузке стационарное ожидание не выдаётся за конечное.
- [ ] При неизвестном числе каналов, конечном буфере, отсутствии нагрузки
  возвращаются корректные `null` и findings, а не вымышленные цифры.
- [ ] **p95/p99 не выводятся из среднего**. Процентильное требование
  помечается неоценённым, пока нет модели распределения или измерений.
- [ ] Для синхронного fan-out максимум средних задержек путей
  **не называется** средним временем завершения параллельного запроса.

## C. Контракты артефактов

- [ ] Канонический файл `<scenario>_performance_analysis.json` всегда
  создаётся после успешной C4 при штатной работе writer.
- [ ] JSON разбирается `PerformanceAnalysisReport.model_validate_json`;
  отсутствующие метрики представлены `null`, а не нулём;
  недопустимые отрицательные/NaN/Infinity отклоняются.
- [ ] PDF создаётся **из того же PerformanceAnalysisReport**; в renderer
  нет расчёта RPS, загрузки или ожидания.
- [ ] PDF открывается, содержит читаемую **кириллицу**, таблицу узлов,
  предупреждения и ограничения; текст можно выделить и найти.
- [ ] Многостраничный документ с длинными именами не теряет строки,
  заголовки таблицы и выводы; нет визуальных наложений.
- [ ] При ожидаемой ошибке необязательного PDF сохраняется JSON,
  `StageStatus.PARTIAL` и объяснение в warning.
- [ ] Статус стадии не путается со статусом полноты самого отчёта
  (`complete`/`partial`/`unavailable`).

## D. Детерминированная интеграция без LLM

- [ ] Есть test fixture со связкой `DesignScenario + ArchitectureGraph`:
  путь **C4 stage outcome → PerformanceAnalysisStage → JSON/PDF** проверен,
  а не просто вызван `report_builder`.
- [ ] Для графа без workload стадия успешно пишет отчёт
  `unavailable` с кодом `workload_missing`.
- [ ] Для небольшого линейного графа заранее вручную рассчитаны
  node RPS, capacity, utilization, queue wait и critical path.
- [ ] Для графа с перегрузкой создаётся `capacity_saturation`
  на **правильном** узле, без `capacity_headroom` на нём же.
- [ ] Для fan-out, cache miss и bounded queue покрыто поведение маршрутизации
  и честность предупреждений.
- [ ] Несколько запусков/сценариев не перезаписывают друг друга.
- [ ] При поломке записи обязательного JSON стадия не заявляет
  `SUCCEEDED` и не выдаёт PDF вместо JSON.

## E. Ручные реальные прогоны с LLM

Тестовые YAML содержат **и функциональные, и нефункциональные требования**.
Они проверяют продукт целиком, но не служат «эталоном» для произвольного
LLM-генерированного графа. Каждый сценарий выполняется со своей директорией
артефактов и собственным набором логов.

| Сценарий | Что проверить | Недопустимый результат |
| --- | --- | --- |
| `checkout_baseline.yaml` | последовательная обработка заказа, оплата/уведомление, ненулевой workload, p99 цель в diagnostics | ложное подтверждение p99 по среднему |
| `catalog_read_heavy.yaml` | высокая доля чтения; если LLM добавил cache, проверить cache miss и альтернативные маршруты | отрицательный входящий RPS, пропавшие fallback-предупреждения |
| `notifications_spiky.yaml` | высокий пик; async-ветка не увеличивает критический синхронный путь | очередь асинхронной доставки ошибочно прибавлена к client latency |
| `helpdesk_no_workload.yaml` | JSON создан, `status=unavailable`, warning `workload_missing` | отсутствие отчёта или подмена неизвестной нагрузки нулём |

- [ ] Все четыре YAML проходят Pydantic-валидацию без LLM.
- [ ] Каждый реальный прогон: C4 сформирована, Performance Analysis
  выполнился, JSON валиден, PDF читаем либо есть **обоснованный** warning.
- [ ] Для YAML с функциональными требованиями результаты Sequence/OpenAPI
  проверяются в тех запусках, где эти стадии выполнились; отсутствие
  результатов из-за ошибок LLM **не засчитывается** как успешный E2E.
- [ ] Изучены warnings, JSON, PDF и согласованность параметров; нет
  замаскированных ошибок выполнения, сквозных графов с необоснованными выводами
  или изобретённых обоснований SLO.

## F. Как отправлять логи на ревью

Для каждого прогона приложить:

1. **Git:** head SHA проверяемой ветки, базовый SHA, ссылка на CI run.
2. **Запуск:** точная команда, версия Python, модель/endpoint (без секретов),
   YAML-файл, каталог выхода и **код завершения** процесса.
3. **Лог:** от старта до финального summary, включая traceback, retries,
   warnings, статусы C4/Performance/Sequence/API.
4. **Артефакты:** JSON отчёта; PDF если есть; список путей/размеров;
   C4-граф JSON и сгенерированные Sequence/OpenAPI при наличии.
5. **Что проверить:** ожидаемые findings и ограничения по таблице выше.

Удобно прислать ZIP **без** `.env`, API-ключей, токенов и персональных данных.
Частичный лог без артефактов может подтвердить лишь часть условий.

### Протокол решения по полученным логам

| Исход | Условие | Решение |
| --- | --- | --- |
| **PASS** | Обязательные стадии, схемы, числа и артефакты прошли проверку; все блокирующие пункты закрыты | Можно обсуждать merge #90 |
| **PASS WITH WARNINGS** | Результат валиден, но часть метрик неоценена **по явно документированной причине** | Не означает, что p95/p99 проверены; нужен ручной review ограничений |
| **FAIL** | Ошибка CI, нарушения схемы/математики, отсутствующий обязательный JSON, ложные claims, поломанные стадии без объяснения | Merge запрещён |
| **INCONCLUSIVE** | Нет полного лога, SHA, C4-графа или отчёта; недостаточно оснований проверить claims | Запросить недостающие артефакты, не выдавать PASS |

**Важно:** даже PASS отдельного YAML-прогона не равен финальному GO.
Merge #90 допустим только после интеграции всех дочерних PR,
прохождения полного CI на его итоговом SHA, закрытия E2E-матрицы
и ручного визуального review PDF.
