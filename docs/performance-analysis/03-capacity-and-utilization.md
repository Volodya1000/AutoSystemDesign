# Расчёт пропускной способности и загрузки

## Назначение

Первый сборщик отчёта заполняет входящий поток запросов, расчётную пропускную способность и коэффициент загрузки. Он использует текущие доменные функции и не реализует вторую версию валидатора. Оценка задержки и ожидания в очереди пока остаётся недоступной: эти поля сериализуются как `null`, а не как ноль или выдуманная оценка.

Реализация: [`report_builder.py`](../../src/application/performance_analysis/report_builder.py). Основной расчёт пропускной способности находится в [`capacity_validator.py`](../../src/domain/specifications/capacity_validator.py), распределение нагрузки — в [`traffic_flow.py`](../../src/domain/specifications/traffic_flow.py). Проверки: [`test_report_builder.py`](../../tests/unit/performance_analysis/test_report_builder.py) и [`test_capacity_validator.py`](../../tests/unit/test_capacity_validator.py).

## Величины и единицы измерения

- \(R_{in}\) — входящий поток запросов, запросов/с.
- \(r\) — число реплик узла.
- \(c\) — значение `maximum_concurrency`, то есть число слотов обработки на реплику в текущей модели.
- \(t\) — среднее время обработки одного запроса, миллисекунд.
- \(R_{capacity}\) — расчётная пропускная способность узла, запросов/с.
- \(\rho\) — коэффициент загрузки, безразмерная величина. Значение больше 1 означает, что расчётная нагрузка превышает модельную пропускную способность.

## Расчёт пропускной способности

В текущей модели каждый слот обслуживания обрабатывает в среднем \(1000 / t\) запросов в секунду. Общее число слотов равно \(r \times c\). Поэтому:

\[
R_{capacity} = \frac{r \times c \times 1000}{t}
\]

Множитель 1000 переводит миллисекунды в секунды. Это формула текущей модели AutoSystemDesign, а не универсальная гарантия реальной пропускной способности приложения. Эквивалентность параметра `maximum_concurrency` числу независимых каналов обслуживания требует отдельного обоснования для конкретного типа компонента.

## Коэффициент загрузки

\[
\rho = \frac{R_{in}}{R_{capacity}}
\]

Пример для одного узла с одной репликой, одним слотом и средним временем обработки 20 мс:

\[
R_{capacity} = \frac{1 \times 1 \times 1000}{20} = 50
\quad \text{запросов/с}
\]

При нагрузке 25 запросов/с:

\[
\rho = \frac{25}{50} = 0{,}5 = 50\%
\]

Если нагрузка составляет 60 запросов/с, загрузка равна \(60 / 50 = 1{,}2\), или 120%. Отчёт сохраняет это значение, а не ограничивает его единицей: иначе важная информация о превышении пропускной способности исчезла бы из JSON.

## Диагностика насыщения

Текущий `CapacitySaturationValidator` сообщает об ошибке, когда \(\rho \ge 0{,}98\). Значение 98% — установленный порог предупреждения с запасом до расчётного предела, а не точка, в которой очередь математически становится бесконечной. При насыщении отчёт создаёт `capacity_saturation` для каждого затронутого узла. Код finding стабилен; его заголовок и описание предназначены только для чтения человеком.

Если профиль нагрузки отсутствует, входящий поток и загрузка не рассчитываются и остаются `null`. Статическую пропускную способность по параметрам узла всё ещё можно показать. Клиентские узлы не имеют модели пропускной способности в текущем контракте, поэтому их значения capacity и utilization тоже `null`, а не ноль.

## Допущения и ограничения

- Пиковая нагрузка равномерно делится между всеми узлами типа Client.
- Узел равномерно делит исходящий поток между своими рёбрами. Модель пока не задаёт веса маршрутизации и кратность вызова каждой зависимости; при нескольких исходящих рёбрах отчёт явно сообщает об этом допущении.
- Cache передаёт далее только долю промахов, заданную параметром hit rate.
- Асинхронные рёбра тоже переносят нагрузку при расчёте входящего RPS.
- Поля среднего ожидания в очереди и среднего времени ответа остаются `null` на этом этапе. Модель очередей, percentiles p95/p99 и SLA по ним здесь не реализованы.
- При отсутствии workload формируется отчёт со статусом `unavailable`; при наличии workload статус `partial`, поскольку этап оценивает только поток и пропускную способность.

Эти допущения отражают текущее поведение кода. Перед построением более сложной модели очередей необходимо отдельно решить неоднозначность между альтернативной маршрутизацией и вызовом каждой зависимости.
