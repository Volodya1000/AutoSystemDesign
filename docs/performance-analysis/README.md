# Анализ производительности

Этот файл служит картой фичи: по нему можно перейти к её контрактам, тестам,
существующим расчётам и точкам интеграции. Каждый PR по анализу производительности
должен обновлять эту карту, когда добавляет или перемещает файлы.

## Размещение нового кода

Новый код группируется по фиче внутри каждого слоя, а не добавляется россыпью в общие
каталоги:

- `src/domain/performance_analysis/` — модели результата и чистые расчёты предметной области.
- `src/application/performance_analysis/` — сборка отчёта.
- `src/application/pipeline/stages/performance_analysis.py` — интеграция отчёта с конвейером.
- `src/infrastructure/performance_analysis/` — адаптеры вывода, в том числе будущий PDF-рендерер.

Папка создаётся, когда в соответствующем слое появляется реальный код; пустые пакеты
заранее не добавляем. Тесты фичи находятся в `tests/unit/performance_analysis/`,
а интеграционные тесты — в `tests/integration/performance_analysis/`.

В приложении `pipeline/stages/` отвечает за orchestration стадий, а `application/services/` — за прикладные операции генерации. Отдельные каталоги `Preparation` и `Internal` не вводятся: сейчас нет самостоятельного этапа подготовки с отдельным контрактом, а `Internal` не обозначает конкретную архитектурную ответственность.

## Существующая логика и метрики

- [Модель узлов](../../src/domain/models/nodes.py) — параметры обслуживания и параллелизма узлов.
- [Модель сценария и профиля нагрузки](../../src/domain/models/scenarios.py) — профиль входного трафика.
- [Модель графа архитектуры](../../src/domain/models/topology.py) — узлы и связи.
- [Режим маршрутизации ребра](../../src/domain/models/edges.py) — типизированное поле `routing_mode`.
- [Расчёт входящего RPS](../../src/domain/specifications/traffic_flow.py) — распределение нагрузки по графу.
- [Расчёт загрузки и валидатор пропускной способности](../../src/domain/specifications/capacity_validator.py).
- [Оценка задержки и критического пути](../../src/domain/specifications/latency_validator.py).
- [Агрегированные метрики проекта](../../src/domain/specifications/metrics.py) — `ProjectMetrics`, сводка для заголовка C4-диаграммы.

`ProjectMetrics` и `NodePerformanceMetrics` описывают разные уровни: агрегированную
сводку проекта и детализацию отдельного узла. Сборщик переиспользует существующие функции
распределения нагрузки, расчёта загрузки и критического пути, а пропускная способность
рассчитывается общей функцией `compute_node_capacity_rps`. Промежуточные словари метрик
имеют явные типы, например `capacity_by_node: dict[str, float]`. Вторая реализация формул
не вводится. Универсальный
класс метрики с ограничением значения диапазоном `[0, 1]` не подходит для RPS,
миллисекунд и коэффициента загрузки, который может быть больше единицы.

Существующие проверки пропускной способности находятся в
`tests/unit/test_capacity_validator.py`; тесты потока проверяют альтернативную
маршрутизацию, fan-out, смешение режимов и долю промахов cache.

## Точки интеграции конвейера

- [Композиция зависимостей](../../src/infrastructure/composition.py) — подключение новых стадий и адаптеров.
- [Контекст стадии](../../src/application/pipeline/context.py) — доступ к сценарию и результатам предыдущих стадий.
- [Контракт стадии](../../src/application/pipeline/stage.py) — `StageId` для зависимостей, контекста и результатов конвейера.
- [Исполнитель конвейера](../../src/application/pipeline/runner.py) — порядок запуска и зависимости стадий.
- [Порт записи артефактов](../../src/application/pipeline/ports.py) — граница между приложением и сохранением результатов.
- [Файловая реализация записи](../../src/infrastructure/persistence/artifact_writer.py) — текущая запись текстовых артефактов.

Стадия `performance_analysis` встроена после C4 и зависит только от его графа. Профиль
нагрузки берётся из исходного `DesignScenario`; зависимость от Sequence и API не нужна.
Стадия записывает `<scenario>_performance_analysis.json`. Отсутствие профиля нагрузки или
частичные метрики остаются статусом внутри отчёта и не превращаются в ошибку конвейера,
если сам JSON-артефакт успешно создан.

## План развития

Полная последовательность этапов, зависимости, критерии приёмки и ограничения
описаны в [ROADMAP.md](ROADMAP.md), который является единственным источником
истины для порядка работ.

Текущее состояние интеграционной ветки:
- PR #90 содержит контракт отчёта, сборку метрик пропускной способности и JSON-стадию.
- PR #99 задаёт семантику альтернативной маршрутизации, fan-out и cache miss path.
- Ветка `fix/performance-latency-slo-semantics` устраняет смешение среднего времени
  ответа и процентильных SLA.
- Ветка `feat/performance-mm1-model` добавляет независимую проверенную модель M/M/1,
  не подключая её автоматически ко всем узлам графа.
- Ветка `feat/performance-mmc-model` добавляет M/M/c и отдельный параметр
  `service_channels_per_replica`; `maximum_concurrency` не используется как его заменитель.
- Следующие этапы: проверенные модели M/M/1 и M/M/c, ревизия аппроксимации G/G/c,
  интеграция очередных метрик, ограниченные буферы, диагностика, PDF и end-to-end
  сценарии.

Параллельное выполнение стадий остаётся условным этапом: оно допустимо только
при измеримой пользе, а не ради усложнения runner-а.
