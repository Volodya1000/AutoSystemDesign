## Как связаны PR

Исторически использовались **вложенные ветки**: дочерний PR базируется на предыдущем.
Надпись \`Merged\` на дочернем PR означает merge в **его base-ветку**, а не обязательно в \`master\` и даже не обязательно в корневой #90.
Перед итоговым merge необходимо убедиться, что изменения из самой глубокой ветки
действительно добрались до интеграционной ветки #90. Проверять следует содержимое,
историю Git и полный CI итоговой ветки.

**Порядок для чтения:** таблица сверху вниз.
**Порядок для интеграции:** проверять достижимость коммитов снизу вверх, не путать её с хронологией закрытия PR.
При наличии несогласованных веток не сливать #90 вслепую.

## На что смотреть в каждом PR

1. **Why**: какую ситуацию исходный код моделировал неправильно или не умел моделировать?
2. **Contract**: что означает новый параметр и чем \`null\` отличается от нуля?
3. **Test**: какой пример рассчитан вручную и какое наблюдаемое поведение проверяется?
4. **Limitations**: что модель *не* имеет права утверждать?
5. **CI**: проверять запуск на конечном head SHA, а не на одном из старых коммитов.

Если PR трудно понять, сначала открыть соответствующий файл \`docs/performance-analysis/NN-*.md\`
и воспроизвести ручной числовой пример. Чтение всего diff подряд — крайне неэффективный учебник.
