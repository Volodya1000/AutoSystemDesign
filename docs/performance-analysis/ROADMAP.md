## 1. Цель

Добавить в AutoSystemDesign анализ производительности с понятным и проверяемым результатом. Пользователь должен получать не только архитектурные диаграммы, Sequence и OpenAPI, но и структурированный отчёт, который объясняет:

- какая расчётная нагрузка поступает на компоненты;
- какова расчётная пропускная способность и загрузка компонентов;
- где обнаружен риск насыщения;
- какие оценки времени ожидания и задержки допустимо рассчитать;
- какие допущения использованы и чего модель не умеет оценивать.

Работу нужно вести **от пользовательского результата к расчётам**. Сначала фиксируется формат результата, затем формируется отчёт на базе уже существующих расчётов, после этого добавляются новые модели массового обслуживания и только потом человекочитаемая визуализация.

Каждая стадия должна быть отдельным небольшим PR с тестами, проверяемыми вручную примерами и учебным Markdown-документом. Разработка ведётся в стиле TDD: определить ожидаемое поведение → написать тест → убедиться, что тест падает по ожидаемой причине → реализовать минимальное решение → проверить регрессию и CI.

## 2. Результат и границы первой версии

### 2.1. Основной результат

**JSON является каноническим артефактом** анализа. Он предназначен для сохранения результата, тестирования, последующего использования из REST API и генерации альтернативных представлений.

Базовая модель результата задаётся в PR #90 и включает:

- идентификатор сценария;
- статус полноты анализа;
- метрики компонентов;
- диагностические выводы с типизированными кодами.

Поля `schema_version` и свободный список `assumptions` в первоначальный контракт не входят:
сейчас они не имеют действующего потребителя и полностью определённого жизненного цикла.
Версионирование следует вводить вместе с опубликованной JSON Schema/API и правилами
обратной совместимости. Структурированные допущения добавляются, когда расчётные модели
начнут производить конкретные допущения; формат должен включать стабильный тип и понятное
описание, а не произвольные строки.

Поля, для которых нет обоснованного значения, должны быть `null`, а не `0`. Ноль означает реальное нулевое значение, `null` означает, что оценка неизвестна или неприменима.

### 2.2. PDF

PDF рассматривается как **дополнительный отчёт для чтения человеком**, создаваемый из той же модели, что и JSON. Он не должен содержать отдельной математической реализации или вычислять показатели заново.

PDF добавляется только после того, как JSON-контракт и значения отчёта стабилизированы. В первой версии PDF должен объяснять выводы, а не просто превращать JSON в распечатку.

### 2.3. Что не входит в начальный объём

- Запуск реальных нагрузочных испытаний или моделирование фактической инфраструктуры.
- Утверждения о точности модели без проверки на независимых эталонных примерах.
- Вывод p95/p99 из одного только среднего времени отклика.
- Автоматическое изменение архитектуры для устранения узких мест.
- Новый REST-сервер в рамках этой фичи. Контракт JSON должен быть пригоден для будущего API, но сам API создаётся отдельно.
- Полная перестройка конвейера ради параллельного запуска до измерения пользы от такой оптимизации.

## 3. Архитектурные правила

### 3.1. Изоляция по фиче внутри слоёв

Новый код должен быть сгруппирован по фиче, чтобы его можно было найти, изучить и изменить, не разыскивая связанные части по всему проекту.

Целевое размещение:

| Слой или назначение | Путь | Ответственность |
| --- | --- | --- |
| Domain | `src/domain/performance_analysis/` | Модели результата, чистые математические расчёты, ограничения и термины предметной области |
| Application | `src/application/performance_analysis/` | Сборка отчёта и orchestration анализа; стадия должна реализовывать существующий контракт `PipelineStage` |
| Infrastructure | `src/infrastructure/performance_analysis/` | Внешние представления и адаптеры, например PDF-рендерер, когда он действительно появится |
| Unit-тесты | `tests/unit/performance_analysis/` | Изолированное поведение моделей и расчётных функций |
| Интеграционные тесты | `tests/integration/performance_analysis/` | Проверка прохождения результата через реальные границы приложения без обязательного вызова LLM |
| Учебные материалы и карта файлов | `docs/performance-analysis/` | Формулы, допущения, примеры, источники и ссылки на код/тесты |

Папки создаются по мере появления содержимого. Нельзя добавлять пустые пакеты заранее. Если соглашения текущего слоя требуют разместить компонент в стандартном каталоге, например в `application/pipeline/stages/`, это нужно зафиксировать в карте фичи и сохранить понятное имя `performance_analysis`.

### 3.2. Не дублировать текущую реализацию

Перед написанием новой формулы или валидатора необходимо проверить и использовать существующие части:

- `src/domain/specifications/traffic_flow.py` — расчёт входящей нагрузки по графу;
- `src/domain/specifications/capacity_validator.py` — текущий расчёт пропускной способности и риска насыщения;
- `src/domain/specifications/latency_validator.py` — оценка задержки узлов и критического пути;
- `src/domain/models/nodes.py` — параметры узлов, включая параллелизм и размер очереди;
- `src/domain/models/scenarios.py` — профиль нагрузки и сценарий;
- `src/application/pipeline/` — контракт стадии, контекст, результат и исполнитель;
- `src/infrastructure/persistence/artifact_writer.py` — существующий порт-адаптер записи текстовых артефактов;
- `src/infrastructure/composition.py` — композиционный корень приложения.

Не создавать второй независимый `AnalyticalQueueingValidator`, если нужную функциональность корректнее встроить в существующие спецификации и сервис отчёта.

### 3.3. Тестируемость

- Domain-расчёты должны быть детерминированными и не выполнять I/O.
- Unit-тесты не должны требовать запущенной LLM, сети или PlantUML-сервера.
- Числовые ожидания сначала проверяются вручную или независимым расчётом.
- Тесты проверяют поведение и свойства результата, а не точный текст сообщения или внутреннее устройство кода.
- На корректных данных проверяются результаты; на границах — устойчивость; на неподдерживаемых условиях — явная диагностика.
- Не вводить `noqa`, отключения новых правил линтера и обходы ошибок CI без отдельного обоснования.
- Числа в тестах можно оставлять литералами, если они используются в одном месте и легко читаются как ожидаемый результат.

### 3.4. Учебная документация обязательна

Каждый PR с новым поведением создаёт или обновляет соответствующий Markdown-файл. Как минимум он должен содержать:

1. задачу и интуитивное объяснение;
2. определения переменных и единицы измерения;
3. формулу с расшифровкой каждого члена;
4. полностью разобранный числовой пример;
5. предположения и ограничения применимости;
6. ссылку на реализацию и тесты;
7. источники для формулы или теоретического утверждения.

`docs/performance-analysis/README.md` должен содержать карту файлов фичи и обновляться при каждом добавлении или перемещении кода.

## 4. Место в конвейере

Текущий конвейер AutoSystemDesign выполняет стадии последовательно:

`C4 → Sequence → API`.

Анализ производительности логически использует граф C4 и профиль нагрузки сценария. Он не нуждается в Sequence-сценариях или проектировании REST API. Его будущая зависимость должна быть эквивалентна `depends_on = ("c4",)`.

На первом этапе стадию следует интегрировать так, чтобы она выполнялась после C4 и не требовала результатов Sequence/API. Это проверит правильный контракт зависимостей, но **не означает параллельного выполнения**: существующий `PipelineRunner` запускает стадии по списку. Возможность конкурентного запуска рассматривается отдельным PR после измерения реальной пользы. Расчётная часть без LLM может оказаться слишком быстрой, чтобы сложность многопоточного/асинхронного планировщика была оправдана.

Если в сценарии нет профиля нагрузки, валидный диагностический JSON-отчёт со статусом `unavailable` предпочтительнее отсутствующего файла или нулевых метрик. Невозможность выполнить расчёт из-за отсутствующих входных данных не должна автоматически считаться ошибкой генерации всей архитектуры. Ошибка записи обязательного артефакта должна обрабатываться по обычным правилам стадии.

## PR 2. Заполнить отчёт метриками пропускной способности

**Предлагаемая ветка:** `feat/performance-capacity-report`
**Зависит от:** PR 1.
**Цель:** получить первый реально полезный отчёт без внедрения очередей.

### Объём

- Добавить чистую функцию или небольшой доменный компонент для сборки метрик производительности компонентов.
- Использовать существующий расчёт входного RPS и текущую политику оценки пропускной способности. Если расчёт максимального RPS необходимо сделать доступным за пределами текущего валидатора, выделить небольшой публичный метод/функцию вместо импорта внутренней функции с подчёркиванием.
- Заполнять `incoming_requests_per_second`, `estimated_capacity_requests_per_second` и `utilization_ratio`.
- Добавлять структурированный `finding` при достижении принятого порога насыщения; использовать стабильный `code`, а не текст как идентификатор.
- Явно включать в отчёт действующие ограничения распределения нагрузки.

### Проверяемый пример

Для одного узла с одной репликой, одним слотом обслуживания и средним временем обработки 20 мс расчётная пропускная способность равна 50 запросам/с. При 25 запросах/с загрузка равна 0,5 (50%). При входной нагрузке 60 запросов/с загрузка равна 1,2 (120%), а не искусственно ограниченным 100%.

Формула текущей модели:

`capacity_rps = replicas_count × maximum_concurrency × 1000 / mean_processing_time_ms`

`utilization = incoming_rps / capacity_rps`

Это формула **принятой в текущем коде модели**, а не универсальная гарантия реальной пропускной способности сервиса. Интерпретацию `maximum_concurrency` необходимо отдельно документировать и проверить до более сложных очередных моделей.

### Требуемые тесты

- Приведённый расчёт с ручным ожидаемым результатом.
- Загрузка ниже, на и выше порога насыщения.
- Нагрузка 0 на компоненте даёт загрузку 0 при известной пропускной способности.
- Перегрузка не обрезает значение загрузки до 1.
- Отсутствие профиля нагрузки даёт статус/диагностику недоступности, а не ложные нули.
- Данные разных компонентов остаются привязаны к их идентификаторам.
- JSON отчёта сериализуется и валидируется текущей Pydantic-моделью.

### Критерии приёмки

- Сборка отчёта не дублирует формулы существующего валидатора.
- Формула и числовой пример описаны в `docs/performance-analysis/03-capacity-and-utilization.md`.
- Пока отчёт содержит только обоснованные метрики; очередь и p99 не подставляются фиктивными значениями.
- Unit-тесты и полный CI проходят.

### Ожидаемый результат

Отчёт можно сформировать в памяти из тестового графа и сценария. Пока он не подключён к обычному CLI-конвейеру.

## PR 3. Добавить стадию конвейера и сохранение JSON

**Предлагаемая ветка:** `feat/performance-analysis-stage`
**Зависит от:** PR 2.
**Цель:** сделать первый результат доступным пользователю при обычном запуске.

### Объём

- Добавить application-компонент анализа, соответствующий контракту `PipelineStage`.
- Зарегистрировать его через `src/infrastructure/composition.py`.
- Использовать существующий `ArtifactWriter`; не вводить отдельный механизм записи файлов без необходимости.
- Сохранять отчёт как `{scenario_identifier}_performance_analysis.json` рядом с остальными артефактами сценария.
- Задать зависимость стадии только от `c4`; в списке стадий разместить её после C4, не меняя пока исполнитель конвейера.
- Не использовать LLM для вычисления метрик.

### Требуемые тесты

- Стадия получает граф C4 через типизированный payload и формирует JSON.
- Стадия не требует payload от Sequence или API.
- Отчёт сохраняется через подменяемый/in-memory `ArtifactWriter`; unit-тест не зависит от файловой системы больше, чем требуется контракту.
- Сценарий без профиля нагрузки создаёт валидный диагностический отчёт и не блокирует дальнейшую генерацию.
- Отсутствующий или некорректный upstream payload обрабатывается существующими правилами зависимостей стадий.
- Интеграционный тест проходит без реального LLM endpoint и проверяет наличие/валидность JSON-артефакта.
- Обычный запуск и запуск с `--no-diagram` по-прежнему могут создавать отчёт.

### Критерии приёмки

## PR 4. Уточнить семантику маршрутизации нагрузки

**Предлагаемая ветка:** `feat/performance-traffic-routing-semantics`
**Зависит от:** PR 3; до добавления расширенных расчётов очередей.
**Цель:** не строить точные очереди на неверно интерпретированном потоке запросов.

### Проблема для решения

Существующая функция делит исходящий RPS узла поровну между его исходящими рёбрами. Это подходит для равновероятной маршрутизации, но не для всех случаев. Например, две независимые синхронные зависимости могут обе вызываться на каждый запрос, то есть обе получать полный поток, а не половину.

### Принятое решение

- `routing_mode=alternative` означает выбор одного из альтернативных рёбер источника; исходящий поток поровну делится между такими рёбрами.
- `routing_mode=fan_out` означает, что каждый запрос вызывает все зависимости этого режима; каждое ребро получает полный исходящий поток.
- У одного источника могут быть fan-out-зависимости и один набор альтернатив. Несколько независимых групп альтернатив и веса маршрутизации пока не поддерживаются.
- Если поле `routing_mode` отсутствует в старом JSON, применяется `alternative`, что сохраняет прежнюю семантику и совместимость загрузки.
- Чтение задаётся ребром `compute -> cache`, а база данных получает только долю промахов через синхронное ребро `compute -> database` от того же compute. Cache не инициирует обращения к базе.
- Один compute может читать только из одного cache, поскольку модель не связывает несколько кэшей с отдельными fallback-рёбрами. Неоднозначный граф отклоняется.
- Решение с примерами зафиксировано в `docs/performance-analysis/04-traffic-routing-semantics.md`.

### Объём

- Добавить типизированный режим маршрутизации ребра с совместимым значением по умолчанию.
- Обновить расчёт RPS, whitelist связей, проверку пути промахов кэша и инструкцию генерации.
- Проверить равномерные альтернативы, fan-out, совместное использование режимов, cache hit rate 0/0.8/1 и загрузку старого JSON.
- Отражать в отчёте ограничение равномерного распределения альтернативных маршрутов, но не помечать явный fan-out как неизвестную семантику.

### Требуемые тесты

- Альтернативные рёбра с пиковым потоком 100 запросов/с получают по 50 запросов/с.
- Каждое fan-out-ребро получает все 100 запросов/с.
- Fan-out-зависимость получает полный поток, а две альтернативы одновременно делят его поровну.
- Для нагрузки 100 запросов/с на ребре compute -> cache и hit rate 0, 0.8 и 1.0 fallback-ребро compute -> database получает соответственно 100, 20 и 0 запросов/с.
- Старая структура JSON без `routing_mode` загружается со значением `alternative`.
- Cache без синхронного ребра compute -> database от каждого читающего compute отклоняется.
- Синхронное ребро compute -> database интерпретируется как cache fallback только при наличии синхронного ребра от этого же compute к cache; оно не считается обычной ветвью маршрутизации.

### Критерии приёмки

- Семантика ветвления и fan-out описана однозначно и типизирована.
- Числовые тесты проверяют ожидаемые RPS, не точные тексты сообщения.
- Старые графы без `routing_mode` продолжают загружаться, а новые могут явно задавать fan-out.
- Расчёт, whitelist, validator кэша и prompt согласованы по направлению cache miss path.
- При неизвестных весах альтернатив модель не делает вид, что знает фактическое распределение.

### Ожидаемый результат

Входные интенсивности узлов интерпретируются по явно заданным правилам. Если данных для точной маршрутизации всё ещё нет, отчёт честно указывает соответствующее ограничение.

## PR 5. Разделить среднюю задержку и SLA по процентилям

**Предлагаемая ветка:** `fix/performance-latency-slo-semantics`
**Зависит от:** PR 1; нужен до заявлений о p95/p99.
**Текущая реализация:** finding `latency_not_evaluated`, статус `partial`, удаление проверки p95/p99 по среднему значению и тест поведения repair loop.
**Цель:** устранить смешение средней задержки и процентильного требования.

### Проблема для решения

### Объём

- Проверить все места создания, проверки и отображения `LatencyRequirement`.
- Уточнить семантику требований и существующего расчёта задержки.
- Отделить оценку средней задержки от проверки процентильного SLA.
- Если действующая модель не способна вычислить требуемый процентиль, показывать «не удалось оценить» с диагностикой, а не выдавать среднее за p99. При необходимости расширить доменную модель результата/тип диагностики минимально.
- Не пытаться получить p99 произвольным множителем от среднего.

### Требуемые тесты

- Модель отчёта явно различает среднее время и процентильную цель.

- Реальное превышение поддерживаемого порога продолжает обнаруживаться.
- Текст диагностики можно изменить без переписывания тестов, которые проверяют код и смысл finding.

### Критерии приёмки

- Ни один отчёт или валидатор не называет среднюю задержку p95/p99.
- Нельзя интерпретировать неизвестный процентиль как успешный SLA.
- Поведение repair loop генерации проверено интеграционным тестом, чтобы изменение latency-валидации не вызывало бесконечных повторов.
- Решение и ограничения зафиксированы в `docs/performance-analysis/05-latency-and-slo.md`.

### Ожидаемый результат

Проект корректно сообщает, какую характеристику он рассчитает и какую пока не способен подтвердить.

## PR 14. Решение о конкурентном исполнении стадий (условный)

**Предлагаемая ветка:** `feat/pipeline-independent-stages`
**Зависит от:** наличия корректно интегрированной стадии анализа и измерений времени выполнения.
**Статус:** не обязательный для первой версии; выполняется, только если есть измеримая польза.

### Предпосылки

- Стадия performance analysis зависит только от C4.
- Sequence зависит от C4.
- API в текущем конвейере зависит и от C4, и от Sequence.
- Текущий `PipelineRunner` выполняет стадии по очереди и проверяет зависимости на основании порядка в списке.

### Объём

- Сначала измерить длительность стадии анализа на репрезентативных графах.
- Если выигрыш оправдывает сложность, отдельно спроектировать исполнение независимых стадий по DAG зависимостей.
- Гарантировать, что API стартует только после завершения требуемых upstream-стадий.
- Сохранить детерминированность отчёта, обработку отказов, status `PARTIAL` и `FAILED`, а также понятный итоговый вывод.
- Не запускать два этапа параллельно только ради формального «мы можем»: расчёт может быть слишком быстрым, чтобы это что-либо улучшило.

### Требуемые тесты

- Независимые стадии могут исполняться одновременно только при готовых зависимостях.
- Зависимая стадия ждёт все необходимые upstream-результаты.
- Ошибка C4 блокирует стадии, которые используют граф.
- Ошибка необязательного PDF не приводит к повреждению JSON.
- Отчёт о запуске содержит результаты всех стадий в стабильной форме.
- Интеграционные тесты не зависят от порядка завершения параллельных задач.

### Критерии приёмки

- Есть benchmark или измерение, подтверждающее выгоду, либо PR закрывается как нецелесообразный.
- Параллельное исполнение не меняет содержимое артефактов и семантику ошибок.
- Рефакторинг runner-а не включён в PR с новыми формулами или PDF.
- Архитектурные тесты импортов и полный CI проходят.

### Ожидаемый результат

Либо сохраняется простой последовательный runner с обоснованием, либо появляется отдельная проверенная поддержка DAG-исполнения. Отсутствие конкурентного запуска не блокирует основную функциональность.

## 6. Общие критерии приёмки любого PR

Каждый PR по этой фиче должен удовлетворять всем применимым пунктам:

1. **Ограниченный объём:** одна основная возможность или одно исправление; не смешивать расчёт, pipeline, PDF и изменение runner-а в одном PR.
2. **TDD:** тест с ожидаемым поведением существует до реализации, падение проверено по ожидаемой причине.
3. **Математическая проверка:** численные примеры ручные или сверены с независимой реализацией/источником.
4. **Пояснение:** изменена соответствующая документация, описаны единицы и допущения.
5. **Карта фичи:** добавлены точные ссылки на новые файлы и изменённые места существующего кода.
6. **Качество:** Ruff, форматирование, mypy, Pylint, architecture import checks и unit-тесты проходят.
7. **Без внешней зависимости:** unit-тесты не требуют LLM, PlantUML или интернет-сервиса.
8. **Обратная совместимость:** существующие сценарии и артефакты не ломаются молча; формат JSON имеет версию.
9. **Честная диагностика:** неизвестная метрика не заменяется нулём; неподдерживаемый percentile не помечается как выполненный SLA; аппроксимации называются аппроксимациями.
10. **Проверяемое ревью:** описание PR кратко объясняет пользовательский результат, математическое изменение и проверку, которая подтверждает его корректность.

PR не считается завершённым только потому, что локальные тесты прошли. Нужен успешный CI, просмотр diff и обновлённая карта фичи.

## 8. Источники и теоретическая база

В каждом файле с формулами конкретный источник должен быть привязан к той формуле, для которой он использован. Следующие материалы — отправная точка для дальнейших PR, а не замена проверки реализации:

- [Queueing Theory — Nader Mehravari, Wiley](https://onlinelibrary.wiley.com/doi/10.1002/047134608X.W4208): обзор моделей очередей и их применений.
- [Queueing Theory — Mark S. Daskin, Wiley, глава в Service Science](https://onlinelibrary.wiley.com/doi/10.1002/9780470877876.ch3): метрики очередей, закон Литтла, марковские модели и численное решение.
- [M/M/c Queues and Erlang C Formula — учебное изложение](https://students.aiu.edu/submissions/profiles/resources/onlineBook/W2g8f2_communication%20networks.pdf): постановка M/M/c, условия устойчивости и формула Эрланга C.
- [A Review of L = λW and Extensions — Ward Whitt, Queueing Systems](https://www.columbia.edu/~ww2040/ReviewLlamW91.pdf): обзор закона Литтла и условий его применения.
- [A Proof for the Queuing Formula: L = λW — John D. C. Little, Operations Research](https://doi.org/10.1287/opre.9.3.383): первоисточник классической формулы закона Литтла.

Для аппроксимации Аллена — Каннина необходимо добавить первичный или академический источник именно по выбранной формуле, а затем проверить используемую форму записи и область применимости. Не копировать формулы из случайного блога без сверки с учебником или первоисточником.

## 9. Порядок работы и актуализация roadmap

Перед созданием очередного PR:

1. Проверить статус зависимого PR и текущую ветку `master`.
2. Открыть соответствующий раздел roadmap и убедиться, что критерии ещё актуальны.
3. Проверить существующие тесты и реализацию, прежде чем добавлять дубликаты.
4. В описании PR перечислить конкретные пункты roadmap, которые выполняются.

После слияния PR:

1. Отметить выполненную стадию ссылкой на PR.
2. В карте фичи указать новые файлы, тесты, формулы и точки интеграции.
3. Если реализация изменила план или выявила новое ограничение, обновить roadmap отдельным небольшим изменением.
4. Не считать последующие стадии выполненными только из-за наличия файла или пустого класса — должны быть реализованы поведение, тесты и документация.

**Этапы 1–3 представлены в интеграционной ветке PR #90:** регрессионная база — [PR #92](https://github.com/Volodya1000/AutoSystemDesign/pull/92), сборка отчёта — [PR #96](https://github.com/Volodya1000/AutoSystemDesign/pull/96), интеграция стадии — [PR #97](https://github.com/Volodya1000/AutoSystemDesign/pull/97). Текущий [PR #99](https://github.com/Volodya1000/AutoSystemDesign/pull/99) выполняет этап 4, уточняя режимы альтернативной маршрутизации, fan-out и cache miss path. После его принятия следующим отдельным шагом будет PR 5: разделение средней задержки и percentile SLA. Модели очередей и PDF остаются последующими независимыми этапами.

## 7. Правило ветвления и последовательного ревью

PR #90 — корневой интеграционный PR этой фичи. Пока фича не принята целиком, его не
нужно вливать в `master`. Следующие PR по roadmap создаются отдельными ветками, но
их целевой base — ветка `feat/performance-analysis-report-contract` из PR #90, а не
`master`. После ревью каждый следующий небольшой PR вливается в эту интеграционную
ветку; так PR #90 постепенно собирает всю фичу и остаётся единым итоговым diff для
финальной проверки.

Перед созданием следующего PR:

1. Свериться с зависимостями и критериями соответствующего этапа roadmap.
2. Проверить, что предыдущий этап принят и его CI прошёл.
3. Создать ветку от актуальной интеграционной ветки и открыть PR в неё.
4. Не включать в один PR независимые формулы, интеграцию pipeline и PDF.
5. После выполнения всех этапов и финальной проверки вливать корневой PR #90 в `master`.

Если GitHub показывает в PR #90 изменения из дочерних PR после их слияния, это ожидаемо:
корневой PR намеренно представляет полный итог фичи. Ветки дочерних PR не должны менять
`master` напрямую.
