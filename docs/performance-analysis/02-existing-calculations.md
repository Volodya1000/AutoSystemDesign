# Существующие расчёты производительности

Этот документ фиксирует поведение доменных расчётов, которое нужно сохранить при
сборке отчёта производительности. Это описание текущей реализации, а не обещание
точности модели реальной системы без проверки её допущений.

## Входящий поток запросов

Реализация: `src/domain/specifications/traffic_flow.py`,
функция `compute_node_incoming_rps`.

- Входная нагрузка берётся из `WorkloadProfile.peak_requests_per_second`.
- Пиковая нагрузка равномерно распределяется между всеми узлами типа Client.
- Каждый узел распределяет исходящий поток поровну между исходящими рёбрами.
- Cache передаёт дальше только долю промахов: входящий поток, умноженный на
  `1 - cache_hit_rate_probability`. Поток, приходящий в сам cache, не уменьшается.
- Все узлы присутствуют в результате. Если клиентов нет, каждому узлу назначается
  нулевой входящий поток.
- Циклический граф отклоняется защитной проверкой топологической сортировки.
- Асинхронные рёбра также переносят нагрузку при расчёте RPS.

Распределение поровну является текущим допущением модели. Оно не учитывает веса рёбер,
условия маршрутизации, read/write ratio или фактическую политику балансировщика.

## Пропускная способность и загрузка

Реализация: `src/domain/specifications/capacity_validator.py`.

Для узла с ограниченной пропускной способностью расчётная максимальная скорость:

`max_rps = replicas_count * maximum_concurrency * 1000 / mean_processing_time_milliseconds`

Множитель 1000 переводит миллисекунды в секунды. Загрузка равна входящему RPS,
делённому на `max_rps`. Клиентские узлы не включаются в результат загрузки; узлы
с нулевым входящим потоком всё равно получают значение 0.

`CapacitySaturationValidator` сообщает ошибку при загрузке, большей или равной 0.98.
Это установленный в коде порог безопасности, а не утверждение, что очередь математически
становится бесконечной именно при 98% загрузки. В расчёте загрузки также не учитываются
различия между типами узлов, кроме общих полей пропускной способности.

## Задержка и критический путь

Реализация: `src/domain/specifications/latency_validator.py`.

- Среднее время обслуживания задаётся в миллисекундах.
- Число параллельных слотов обслуживания рассчитывается как произведение числа реплик
  и `maximum_concurrency`.
- Для очереди используется аппроксимация Allen–Cunneen с пуассоновским входящим потоком
  (`c_a^2 = 1`) и коэффициентом вариации обслуживания, вычисляемым из стандартного
  отклонения и среднего времени обработки.
- Если входящая нагрузка достигает или превышает расчётную суммарную скорость обслуживания,
  время пребывания в узле возвращается как бесконечность.
- Критический путь строится только по синхронным рёбрам; задержка ребра добавляется
  между вкладом исходного и целевого узлов. Асинхронные рёбра не увеличивают задержку
  синхронного критического пути.
- При отсутствии профиля нагрузки результат критического пути отсутствует (`None`).

Это оценка среднего времени, а не расчёт p95 или p99. Нельзя получать эти перцентили
умножением среднего на фиксированный коэффициент. Перед расширением отчёта нужно
отдельно проверить корректность допущений очереди и семантику параметров параллелизма.

## Агрегированные метрики проекта

Реализация: `src/domain/specifications/metrics.py`, функция `compute_project_metrics`.

- Максимальная загрузка и идентификатор соответствующего узла берутся из расчёта загрузки.
- Задержка критического пути берётся из `compute_critical_path`.
- Месячная стоимость суммируется по узлам с ограниченной пропускной способностью.
- Если задано несколько бюджетных ограничений или SLA по задержке, для сводки выбирается
  минимальный порог соответствующего типа.
- При отсутствии нагрузки загрузка и задержка не рассчитываются, но стоимость остаётся
  доступной.

## Тестовая стратегия

Существующие тесты пропускной способности уже проверяют порог 98%, границу 97.99%/98%,
перегрузку и влияние реплик. Новые регрессионные тесты потока запросов независимо
проверяют линейную цепочку, несколько клиентов, разветвление, cache miss-rate, граф без
клиентов и отклонение циклов.

Тесты должны проверять числовые результаты и смысловые свойства, а не точные формулировки
ошибок или внутренний порядок вызовов. Новые тесты не меняют формулы и не требуют LLM.
