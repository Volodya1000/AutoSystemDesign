# Этап 13: сквозные регрессии и контракт JSON v1

## Зачем тестировать конвейер, если unit-тесты формул уже есть

Неправильная интеграция может испортить результат даже при правильных
M/M/1, M/M/c и G/G/c: например, потерять профиль workload, перепутать
C4 payload, не записать JSON, рассчитать метрики повторно в PDF или
испортить вывод одного прогона другим.

Тест [test_pipeline_integration.py](../../tests/unit/performance_analysis/test_pipeline_integration.py)
проверяет **настоящий** `PipelineRunner`, `PerformanceAnalysisStage`,
`FileSystemArtifactWriter` и `PerformanceReportPdfRenderer`.
Подменяется **только C4-генерация LLM**: вместо неё детерминированная
стадия предоставляет заранее проверенный `ArchitectureGraph` и
сохраняет его JSON. Таким образом результат воспроизводим без LLM,
сетевого соединения, случайного вывода и внешних рендер-серверов.

### Проверяемые случаи

| Случай | Ручной эталон или инвариант |
| --- | --- |
| Линейный `client -> service` | При λ=10 RPS и E[S]=50 мс: capacity=20 RPS, ρ=50%, Wq=50 мс, W=100 мс; вместе с задержкой ребра 1 мс критический путь=101 мс |
| Workload отсутствует | Обязательный JSON и PDF получены; `status=unavailable`, код `workload_missing`; время ожидания не подменяется нулём |
| Перегрузка λ=30, μ=20 | ρ=150%, saturation; не возвращается конечная стационарная оценка ожидания |
| Независимые прогоны | Разные output-directory, идентификаторы сценария, графы и PDF не смешиваются |

Каждый тест читает **сохранённый** JSON по Pydantic-модели. В некоторых
сценариях PDF дополнительно проверяется извлечением текста, то есть
проверяется и связка application → infrastructure → filesystem.

Запуск:

```bash
uv run pytest -m unit tests/unit/performance_analysis/test_pipeline_integration.py
```

## Публикация JSON Schema

Каноническая модель `PerformanceAnalysisReport` объявляет
`schema_version: Literal["1.0"]`. Если старый JSON не содержит поля,
по умолчанию он интерпретируется как `1.0`; несовместимая версия
(например `2.0`) должна быть отклонена.

Публичный файл:
[report.schema.json](report.schema.json).

**Источник истины — Pydantic-классы**, а не вручную написанная схема.
Для обновления после согласованного изменения контракта:

```bash
uv run python scripts/export_performance_schema.py --write
```

Для воспроизводимой сверки, в том числе в CI:

```bash
uv run python scripts/export_performance_schema.py
```

Вторая команда лишь сравнивает файл со сгенерированным результатом
и возвращает ненулевой код завершения при расхождении. CI не должен
молча переписывать опубликованный контракт.

**Версионирование:** `1.0` — текущая версия формата, а не
«версия алгоритма». Изменение его обязательных полей, единиц измерения
или значения старых полей требует отдельно рассмотренной совместимости
и осознанного обновления версии. Добавление необязательных полей,
сохраняющее чтение старого JSON, допустимо в рамках текущей версии,
если об этом сказано в changelog и обновлена схема.

## Что остаётся на ручную приёмку

Offline-тесты **не могут** доказать, что конкретная LLM на конкретных
требованиях всегда выдаст валидный C4. На этапе финального объединения
нужно пройти реальные YAML-сценарии и передать логи/артефакты по
[корневому чек-листу](ROOT_PR_ACCEPTANCE.md).

До переноса всего набора дочерних изменений в головную ветку
[PR #90](https://github.com/Volodya1000/AutoSystemDesign/pull/90)
и полного CI на **итоговом** SHA слияние в master остаётся заблокированным.
