# Контракт отчёта о производительности

## Назначение

Отчёт — структурированный результат анализа архитектуры. Его можно сохранять в JSON,
позднее возвращать через REST API и отображать в PDF. Математические вычисления,
запуск конвейера и рендеринг здесь не реализуются: сначала фиксируется понятный контракт.

## Поля верхнего уровня

| Поле | Значение |
| --- | --- |
| `schema_version` | Версия формата данных, сейчас `1.0`. |
| `scenario_identifier` | Идентификатор YAML-сценария. |
| `status` | `complete`, `partial` или `unavailable`. |
| `nodes` | Метрики по узлам архитектуры. |
| `findings` | Диагностические сообщения, связанные с рисками или наблюдениями. |
| `assumptions` | Явно указанные ограничения и предположения расчёта. |

Значения статуса означают:

- `complete`: все поддерживаемые расчёты, применимые к сценарию, выполнены.
- `partial`: часть метрик недоступна или некоторые случаи пока не поддерживаются.
- `unavailable`: оценку нельзя выполнить на доступных входных данных.

Точные условия выставления статуса будут закреплены тестами при интеграции отчёта с расчётами.

## Метрики узла

| Поле | Единица | Смысл |
| --- | --- | --- |
| `node_identifier` | — | Идентификатор узла в C4-графе. |
| `incoming_requests_per_second` | запросов/с | Оценка нагрузки, приходящей на узел. |
| `estimated_capacity_requests_per_second` | запросов/с | Расчётная пропускная способность узла при принятых допущениях. |
| `utilization_ratio` | доля | Отношение нагрузки к расчётной пропускной способности: `0.95` соответствует 95%. Значение может быть больше 1 при перегрузке. |
| `estimated_mean_queue_wait_milliseconds` | мс | Расчётное среднее ожидание в очереди. |
| `estimated_mean_response_time_milliseconds` | мс | Расчётное среднее время пребывания запроса в узле: ожидание плюс обслуживание. |

Метрики, которые невозможно рассчитать, остаются `null`. Ноль имеет отдельный смысл и не
должен использоваться вместо неизвестного значения. Для интерпретации причины отсутствия
метрики отчёт должен содержать соответствующий вывод или допущение.

Эти числа являются расчётными оценками, а не измерениями реальной системы. Контракт пока
не обещает расчёт p95/p99. Средняя задержка сама по себе не определяет высокий процентиль.

## Диагностические сообщения

У `findings` предусмотрены:

- `code` — стабильный машинно-читаемый идентификатор;
- `severity` — `info`, `warning` или `error`;
- `title` и `description` — краткое название и пояснение для человека;
- `affected_node_identifiers` — узлы, к которым относится вывод;
- `recommendation` — рекомендация, если её можно обосновать.

Клиент REST API сможет принимать решения по коду и уровню серьёзности, а не по точному
тексту сообщения. Формулировки поэтому можно будет улучшать без поломки потребителей.

## Пример структуры

Ниже показан пример недоступного анализа, а не фактический результат расчёта:

```json
{
  "schema_version": "1.0",
  "scenario_identifier": "online_store",
  "status": "unavailable",
  "nodes": [],
  "findings": [
    {
      "code": "workload_missing",
      "severity": "warning",
      "title": "Недостаточно данных о нагрузке",
      "description": "В сценарии не задан профиль нагрузки, поэтому оценку производительности выполнить нельзя.",
      "affected_node_identifiers": [],
      "recommendation": "Укажите профиль нагрузки в YAML-сценарии."
    }
  ],
  "assumptions": []
}
```
