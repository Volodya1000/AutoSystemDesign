# Контракт отчёта о производительности

## Назначение

Отчёт — структурированный результат анализа архитектуры. Его можно сохранять в JSON,
использовать позднее в REST API и отображать в PDF. Расчёты и рендеринг в этой модели
не выполняются.

Контракт фиксирует только поля, для которых определены смысл и производитель данных.
Не добавляем поля «на будущее», пока не определено, кто и когда будет их заполнять.

## Поля верхнего уровня

| Поле | Значение |
| --- | --- |
| `scenario_identifier` | Идентификатор YAML-сценария. |
| `status` | Полнота анализа: `complete`, `partial` или `unavailable`. |
| `schema_version` | Версия JSON: прежние файлы 1.0 остаются читаемыми, новая стадия формирует 1.1. |
| `workload` | Для версии 1.1: исходные baseline/peak RPS и `analyzed_profile: peak`. В старых отчётах `null`. |
| `nodes` | Метрики по узлам архитектуры. |
| `findings` | Диагностические сообщения, связанные с рисками или наблюдениями. |
| `estimated_longest_synchronous_path_mean_milliseconds` | Максимум средних оценок **синхронных путей** от клиента в миллисекундах, а не среднее время завершения параллельного запроса. При недоступной оценке `null`. |
| `critical_path_node_identifiers` | Узлы выбранного синхронного пути. Пустой список, если путь не оценён. |

### Статус отчёта и статусы генерации

`PerformanceAnalysisStatus` описывает **полноту анализа производительности**:

- `complete`: выполнены все применимые расчёты, поддерживаемые текущей версией.
- `partial`: часть метрик не рассчитана либо некоторые условия пока не поддерживаются.
- `unavailable`: входных данных недостаточно, чтобы выполнить расчёт.

Это не то же самое, что `GenerationStatus` в `application/results.py`, который описывает,
успешно ли завершилась генерация и валидация предложения LLM. Это также не `StageStatus`,
который управляет результатом стадии конвейера. Их значения похожи внешне, но отвечают на
разные вопросы и принадлежат разным слоям; импортировать application-статус в domain нельзя.

Новые поля критического пути добавлены в PR 9 и остаются необязательными для
обратной совместимости существующего JSON. Вычисления, тесты и ограничения
описаны в [09-queue-metrics-json-report.md](09-queue-metrics-json-report.md).

## Зафиксированный режим нагрузки

При наличии профиля новая стадия записывает `workload` с исходными `baseline_requests_per_second`, `peak_requests_per_second` и `analyzed_profile = "peak"`. Это означает, что все рассчитанные нагрузки узлов и оценки задержек относятся к **пиковому** профилю, а не к базовому. Поля только переносятся из типизированного входного сценария; они не выводятся из PDF или LLM.

`schema_version="1.1"` добавляет необязательное поле `workload`; отчёты версии 1.0 продолжают разбираться и не получают выдуманные базовые значения. Старые диагностические коды остаются читаемыми, но новые не генерируются.

## Метрики узла

`NodePerformanceMetrics` представляет **набор метрик одного узла**. На первом этапе каждая
метрика остаётся отдельным типизированным полем с единицами и ограничениями, указанными
в имени и валидаторах модели.

| Поле | Единица | Смысл |
| --- | --- | --- |
| `node_identifier` | — | Идентификатор узла в графе архитектуры. |
| `incoming_requests_per_second` | запросов/с | Оценка нагрузки, приходящей на узел. |
| `estimated_capacity_requests_per_second` | запросов/с | Расчётная пропускная способность при принятых допущениях. |
| `utilization_ratio` | доля | Нагрузка, делённая на расчётную пропускную способность. `0.95` означает 95%; значение может быть больше `1.0`, если нагрузка выше пропускной способности. |
| `estimated_mean_queue_wait_milliseconds` | мс | Расчётное среднее время ожидания в очереди. |
| `estimated_mean_response_time_milliseconds` | мс | Расчётное среднее время пребывания запроса в узле: ожидание плюс обслуживание. |

Значения, которые нельзя рассчитать, представлены как `null`. Ноль означает нулевой
результат, а не отсутствие данных.

### Почему здесь пока нет универсального класса Metric с диапазоном 0–1

Метрики имеют разные единицы: RPS, миллисекунды и коэффициент загрузки. Коэффициент
загрузки также должен иметь возможность превысить `1.0`, чтобы отчёт не скрывал перегрузку.
Поэтому общая модель, которая ограничивает любое значение диапазоном `[0, 1]`, здесь была
бы неверной. Отдельную модель для вероятностей/нормированных показателей стоит добавлять
только там, где есть конкретная метрика, для которой такое ограничение действительно
является предметным инвариантом.

Явные типизированные поля намеренно сохраняют удобный JSON-контракт и не позволяют
перепутать единицы измерения. Переход к универсальному списку метрик потребовал бы
отдельного решения по типам, единицам и валидации каждого элемента, а не только общего
базового класса.

## Диагностические сообщения

Новые отчёты генерируют `findings` **только для рассчитанных рисков
насыщения** (`capacity_saturation` при загрузке от 98%). Для каждого
риска сохраняются код, серьёзность, название, описание, затронутый узел
и необязательная рекомендация. Значения всех метрик находятся в `nodes`.

Не генерируются дополнительные сообщения о низкой загрузке, неподдерживаемой
модели, непроверенном p99 или конечной очереди. Неизвестные численные
значения остаются `null`, статус расчёта сохраняется в `status`.
Это не означает, что отсутствующее требование выполнено.

Для **чтения исторических JSON версии 1.0** типизированные enum сохраняют
старые диагностические коды. Новые отчёты их не производят, но старые
файлы остаются валидными. Контракт полей и типы не изменились, поэтому
`schema_version` остаётся `1.0`.

## Версия и предположения

В текущей опубликованной JSON Schema присутствует `schema_version: "1.0"`.
Свободного списка предположений `assumptions` в схеме нет: параметры и
доступность показателей представлены отдельными типизированными полями.
Читателям PDF не показываются списки того, что модель не умеет рассчитать.

## Пример структуры

Пример ниже иллюстрирует недоступный анализ, а не фактический результат расчёта:

```json
{
  "scenario_identifier": "online_store",
  "schema_version": "1.0",
  "status": "unavailable",
  "nodes": [],
  "estimated_longest_synchronous_path_mean_milliseconds": null,
  "critical_path_node_identifiers": [],
  "findings": []
}
```

## Связанные файлы и метрики проекта

- Модель результата: [`report.py`](../../src/domain/performance_analysis/report.py).
- Контрактные тесты: [`test_report.py`](../../tests/unit/performance_analysis/test_report.py).
- [Существующие агрегированные метрики](../../src/domain/specifications/metrics.py) — `ProjectMetrics`, сводка по проекту для заголовка диаграммы C4.
- Карта файлов фичи: [`README.md`](README.md).

`ProjectMetrics` и `NodePerformanceMetrics` имеют разные области действия: первое —
проектная сводка для C4, второе — детализация по отдельному узлу в отчёте. Их нельзя
склеить в один объект без потери смысла. При интеграции все вычисления должны переиспользовать
существующие функции из `domain/specifications`; новый отчёт собирает и представляет эти
результаты, а не повторяет формулы.
