# Метрики очередей и оценка критического синхронного пути в JSON

## Контракт

Отчёт `PerformanceAnalysisReport` сохраняет для каждого узла:

- `estimated_mean_queue_wait_milliseconds` — среднее ожидание в очереди;
- `estimated_mean_response_time_milliseconds` — среднее ожидание плюс среднее обслуживание.

На верхнем уровне отчёта также есть:

- `estimated_longest_synchronous_path_mean_milliseconds` — **максимальная сумма средних** задержек узлов и сетевых рёбер на синхронном пути от клиента;
- `critical_path_node_identifiers` — идентификаторы узлов выбранного пути.

Все эти поля оцениваются для заданного профиля нагрузки, а не измеряются в работающей системе. При отсутствии обоснованной оценки значение времени равно `null`, а не нулю или бесконечности. Для старых JSON без двух новых полей применяется `null` и пустой список соответственно.

Важно: `max(E[T_1], E[T_2])` **не равно** `E[max(T_1,T_2)]` при параллельном fan-out. Поэтому новое верхнеуровневое поле названо *longest path mean*, а не *end-to-end request mean*. Оно не является ни p95/p99, ни гарантированной оценкой среднего времени завершения параллельного запроса.

## Математика и допущения

Для одного узла с известными каналами обслуживания используются среднее время \(E[S]\), стандартное отклонение \(\sigma_S\), входящая интенсивность \(\lambda\), число каналов \(c\). Расчёт очереди использует аппроксимацию Allen–Cunneen:

\[
\rho=\frac{\lambda E[S]}{c},\qquad
W_q \approx \frac{1+c_s^2}{2}
\frac{\rho^{\sqrt{2(c+1)}-1}}{c(1-\rho)}E[S],
\quad c_s^2=\frac{\sigma_S^2}{E[S]^2}
\]

Здесь интенсивность поступлений считается пуассоновской, то есть \(c_a^2=1\), поскольку исходный профиль не содержит коэффициента вариации интервалов между поступлениями. При \(c=1\) и \(c_s^2=1\) аппроксимация совпадает с точной M/M/1. При \(c>1\) она остаётся приближением, а не точной M/M/c.

\[
W = W_q+E[S],\qquad
T_{path}=\sum_{n\in path} W_n+\sum_{e\in path} t_e
\]

Заданные в миллисекундах времена обслуживания и рёбер приводятся к одним единицам. Ветви с асинхронным fire-and-forget не продлевают задержку вызывающего синхронного пути, но могут иметь собственные показатели загрузки и ожидания.

## Числовой пример

Линейный граф `client → first → second`, интенсивность 20 запросов/с. По одному каналу обслуживания в каждом узле, время обслуживания экспоненциального вида:

| Узел | Среднее обслуживание | Скорость канала | Среднее ожидание | Среднее время ответа |
|---|---:|---:|---:|---:|
| first | 10 мс | 100 RPS | 2,5 мс | 12,5 мс |
| second | 20 мс | 50 RPS | 13,33 мс | 33,33 мс |

Оба синхронных ребра добавляют по 1 мс. Значение `estimated_longest_synchronous_path_mean_milliseconds` равно примерно **47,83 мс** (12,5 + 33,33 + 2). При параллельных ветвях результатом является максимальная *сумма средних по одному пути*, а не сумма всех ветвей.

## Неподдерживаемые случаи

- При неизвестном `service_channels_per_replica` (и положительной нагрузке) время очереди остаётся `null`; нельзя подставлять `maximum_concurrency` вместо числа независимых каналов.
- При \(\rho \ge 1\) стационарное ожидание недоступно; создаются findings о насыщении/недоступной задержке.
- Конечные буферы `maximum_queue_size` не интерпретируются как бесконечные очереди *без ограничений*: точная модель отказов/потерь и поддержка политики буфера рассматриваются в roadmap PR 10.
- Conditional fallback после cache miss, альтернативные маршруты и синхронный параллельный fan-out требуют дополнительной модели для настоящего общего среднего времени ответа.
- Процентильные p95/p99 не выводятся из средних; `latency_not_evaluated` сохраняется.
