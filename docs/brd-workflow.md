# От BRD до архитектурных артефактов

После `uv sync --locked --all-groups` и настройки LLM запустите из корня проекта:

```powershell
uv run python scripts/generate_from_brd.py `
  --document examples/requirements/online_store_brd.md
```

Это единый запуск извлечения и существующего конвейера. Ручное редактирование
или передача YAML между командами не требуется. Сейчас поддерживается UTF-8
Markdown. Параметры LLM задаются в `config.yaml`; `ASD_BASE_URL` и `ASD_API_KEY`
берутся из окружения или `.env`. Другой конфигурационный файл можно выбрать
переменной `APP_CONFIG_FILE`.

`online_store_brd.md` — компактный пример регистрации и отслеживания заказов
с двумя функциональными требованиями. Более широкий `online_store.md`
содержит оплату, поддержку, неоднозначности и открытые вопросы; его можно
передать той же команде для проверки извлечения сложного документа.

Для доли чтений поддерживается запись `80%`: сначала проверяется буквальное
число и цитата, затем код переводит процент в `read_ratio: 0.8`.
Исходная цитата сохраняется. Число `80` без знака процента не превращается
в долю автоматически; отсутствующее значение также не подставляется.

Для локальной модели установите контекст в LM Studio, достаточный для схем и
подсказок генерации. Значение `llm.context_window_tokens` в конфигурации проекта
само по себе не меняет контекст загруженной модели. В реальном проверочном
запуске извлечение прошло, но C4 был отклонён сервером с `n_ctx: 4096`, тогда
как исходная подсказка требовала более 6000 токенов. Это сбой запуска, а не
успешная генерация архитектуры.

## Что находится на выходе

```text
brd_demo_01/
  requirements.evidence.json
  scenario.yaml
  run.json
  artifacts/
    <scenario>_c4.json
    <scenario>_nfr_coverage.json
    <scenario>_c4.puml
    <scenario>_c4.png
    <scenario>_performance_analysis.json
    <scenario>_performance_analysis.pdf
    <scenario>_roles.json
    <scenario>_seq_<requirement>_ast.json
    <scenario>_seq_<requirement>.puml
    <scenario>_seq_<requirement>.png
    <scenario>_api_design.json
    <scenario>_api_openapi.json
    <scenario>_api_swagger.html
```

Это ожидаемый состав успешного полного запуска, а не обещание наличия файлов
при сбое. Точные имена произведённых файлов перечислены в `run.json`.
PDF зависит от доступности Unicode-шрифта. При `--diagram-format svg`
картинки имеют расширение `.svg`. При `--no-diagram` рендеринг диаграмм
отключается. `--profiles profiles.json` передаёт явные параметры обслуживания
в анализ и проверку C4. `--verbose` включает подробные логи LLM.

По умолчанию используется каталог `output/<document-stem>`. Он должен
отсутствовать: команда не смешивает новый запуск со старыми результатами.
Для повторения укажите новый путь через `--out-dir`.

## Откуда берутся параметры производительности

Для обычного BRD-запуска отдельные JSON и YAML заполнять не требуется. Нагрузка
извлекается из BRD, а параметры узлов для первого чернового расчёта берутся из
сгенерированного C4-кандидата. В `run.json` такой режим отмечен как
`llm_generated_c4_parameters`: это оценка для обсуждения, а не измерение системы.

`--profiles <file.json>` — необязательный режим для повторяемого расчёта. Он
переопределяет параметры обслуживания значениями с явно указанным источником
(`assumption` или `measurement`), а `run.json` получает режим
`explicit_service_profiles`.

Файлы в `examples/performance/` нужны разработчикам и авторам экспериментов:

- `online_store_scenario.yaml` — фиксированный вход без обращения к LLM;
- `online_store_graph.json` — фиксированная архитектура для расчётов и тестов;
- `online_store_profiles.json` — документированные допущения или измерения узлов.

`examples/simulation/cache_demo.json` — отдельный воспроизводимый сценарий
дискретно-событийной симуляции кэша. Эти файлы не являются обязательными полями,
которые архитектор должен подготовить перед запуском из BRD.

## Как читать результат

- `requirements.evidence.json`: цитаты, исключённые или неоднозначные данные.
- `scenario.yaml`: автоматически полученное внутреннее представление требований.
- `run.json`: код завершения, выполненные стадии, их предупреждения, время,
  токены генерации стадий и список файлов. Токены извлечения в эти счётчики
  стадий не входят.
- `<scenario>_nfr_coverage.json`: какие NFR действительно оценены.

Коды завершения совпадают с существующим конвейером: `0` — обязательные
артефакты получены; `1` — нет подтверждённого сценария либо провалена стадия;
`2` — ошибка входа, конфигурации, файловой системы или LLM endpoint.
Необязательный рендеринг может завершиться предупреждением при коде `0`.
Статус `completed` означает завершение конвейера, а не доказательство
выполнения всех NFR. Неоценённые требования остаются видны в покрытии.

Если Sequence не прошёл проверку, API не запускается. Успешные артефакты
предыдущих стадий сохраняются, а запуск отмечается как неудачный. При ошибке
настройки или извлечения в новом каталоге остаётся `run.json` с кодом `2`.

## Демонстрация коллегам

Покажите один исходный BRD, команду выше и итоговую сводку консоли. Затем
откройте C4, Sequence, Swagger и отчёт из того же каталога запуска. Сверьте
число FR и NFR в показанных материалах с извлечением и не заменяйте
отсутствующий результат картинкой от другого сценария.

На слайдах полезно сохранить объяснение структурных проверок, цикла
исправления и расчётов ТМО. Для статьи экспериментальные доказательства
эффективности и дальнейшее сравнение с SimPy остаются отдельной задачей.
