# Фактические сведения для презентации AutoSystemDesign

Этот файл предназначен агенту, который создаёт презентацию для системного архитектора. Используй его вместе с [планом презентации](presentation_plan.md) и [демонстрационным YAML-сценарием](examples/social_network_chat.yaml). Если формулировка из плана расходится с этим файлом или исходным кодом, не усиливай утверждение без проверки.

## Краткое описание

AutoSystemDesign — инструмент поддержки проектирования программных систем. Он принимает сценарий в YAML, с помощью LLM предлагает архитектурную модель, проверяет её по заданным структурным и предметным правилам, а затем формирует связанные архитектурные и API-артефакты.

Главная ценность для демонстрации — сквозная связь между входными требованиями, архитектурным графом, сценариями взаимодействия и спецификацией REST API. Это помощник для подготовки и обсуждения первого варианта решения, а не замена архитектора и не гарантия готовности к production.

## Что принимает инструмент сейчас

Основной формат входа — YAML-сценарий. Пример находится в `docs/examples/social_network_chat.yaml`; соответствующий сценарий в репозитории — `scenarios/social_network_chat.yaml`.

В сценарии описываются:
- идентификатор и описание проекта;
- профиль нагрузки: базовые и пиковые запросы в секунду, доля чтений;
- нефункциональные требования, представленные типизированными моделями;
- функциональные требования с идентификаторами, названиями и текстовым описанием.

Текущая версия не принимает произвольные документы BRD, PDF или DOCX как готовый входной формат. Отдельного графического интерфейса нет: запуск производится через CLI, настройки задаются в `config.yaml` и переменных окружения.

Для демонстрационного сценария `social_network_chat` указаны 500 запросов/с в базовом режиме, 2500 запросов/с в пике, доля чтений 0.6, требование к задержке с порогом 150 мс на 99-м перцентиле и требование доступности 99.99%. В нём два функциональных требования: доставка личного сообщения онлайн/офлайн и подтверждение прочтения.

**Важная оговорка о требованиях:** наличие типа требования в модели сценария не означает, что для него уже подключён активный валидатор. В текущей сборке сервиса архитектуры подключены проверки бюджета, насыщения вычислительных узлов и теоретической задержки. Типы доступности, размера очереди и использования ресурсов существуют в моделях, но не все из них имеют подключённую специализированную проверку в текущей композиции. Не утверждать, что каждое NFR из YAML проверяется автоматически.

## Конвейер и результаты

Конвейер состоит из трёх этапов:

1. **C4:** генерация доменной модели архитектурного графа, структурная и семантическая проверка, построение C4 Container Diagram.
2. **Sequence:** генерация каталога бизнес-ролей и отдельного структурированного сценария взаимодействия для каждого функционального требования.
3. **API:** генерация модели REST API, её проверка, создание спецификации OpenAPI 3.1 и HTML-представления Swagger UI.

Sequence и API пропускаются, если в сценарии нет функциональных требований. Успешная генерация модели и рендеринг изображения являются разными результатами: изображение может не сформироваться, хотя обязательная структурированная модель сохранена. В таком случае этап может завершиться со статусом PARTIAL; код завершения CLI сам по себе не гарантирует, что все изображения созданы.

Для сценария с идентификатором `social_network_chat` типичные имена файлов:
- `social_network_chat_c4.json` — модель архитектурного графа;
- `social_network_chat_c4.puml` и `social_network_chat_c4.png` или `.svg` — исходник C4-диаграммы и изображение, если рендеринг включён и успешен;
- `social_network_chat_roles.json` — каталог бизнес-ролей;
- `social_network_chat_seq_req_msg_01_ast.json` и соответствующие `.puml`/изображение — сценарий взаимодействия для требования `req_msg_01`;
- аналогичные файлы с суффиксом `req_msg_02` для второго требования;
- `social_network_chat_api_design.json` — доменная модель REST API;
- `social_network_chat_api_openapi.json` — спецификация OpenAPI 3.1;
- `social_network_chat_api_swagger.html` — HTML-представление API.

Фактический набор файлов зависит от успешности этапов и настройки рендеринга. Презентация не должна выдавать эти имена за доказательство конкретного успешного запуска: сначала выполни реальный запуск и проверь выходную папку.

## Архитектурная модель и строгая проверка

LLM предлагает типизированный граф, но результат не принимается на веру.

**Разрешённые типы вершин:** `client`, `load_balancer`, `compute`, `database`, `cache`, `message_broker`. Данные каждой вершины разбираются в соответствующую модель; лишние поля для моделей узлов запрещены.

**Белый список типов связей:** пары «источник → назначение» проверяются отдельно. По умолчанию разрешены:
- `client → load_balancer`;
- `client → compute`;
- `load_balancer → compute`;
- `compute → compute`;
- `compute → database`;
- `compute → cache`;
- `compute → message_broker`;
- `message_broker → compute`.

**Структурные проверки:** уникальность идентификаторов вершин, наличие обеих конечных вершин у каждой связи, соответствие пары типов вершин белому списку, отсутствие циклов и изолированных вершин в графе с несколькими вершинами.

**Семантические проверки архитектуры:** проверка связи производителя и потребителя у брокера сообщений; проверка использования кэша и резервного пути при промахе; расчёт загрузки вычислительных узлов и проверка порога насыщения 98%; расчёт теоретической задержки критического синхронного пути; проверка суммарной месячной стоимости относительно бюджетного ограничения, если оно задано.

Эти проверки находят известные классы структурных и модельных нарушений. Они не доказывают оптимальность решения, реальную производительность или пригодность архитектуры к эксплуатации без инженерной проверки.

## Проверки Sequence и API

Для Sequence результат включает каталог бизнес-ролей, а для каждого функционального требования — типизированный сценарий взаимодействия.

Проверки Sequence включают:
- отсутствие повторяющихся идентификаторов ролей и линий жизни;
- ссылки пользовательских участников на существующие бизнес-роли;
- ссылки технических участников на узлы C4;
- соответствие идентификатора требования тому, для которого строится сценарий;
- обязательное использование каждой объявленной линии жизни хотя бы в одном сообщении;
- запрет на использование одного клиентского компонента C4 двумя разными бизнес-ролями;
- обязательную асинхронную маркировку сообщений типа `event` и `notification`.

Для API проверяются уникальность `operation_id`, коллизии маршрутов с учётом шаблонов переменных, соответствие параметров пути переменным в URL, ссылки на объявленные схемы, ссылки на существующие компоненты C4 и идентификаторы известных функциональных требований.

## Роль LLM и генерация диаграмм

LLM возвращает JSON-представление доменных объектов:
- архитектурный граф;
- каталог ролей и AST сценария взаимодействия;
- описание API с операциями, параметрами, ответами и схемами.

После этого результат извлекается из ответа, разбирается в Pydantic-модель и проходит проверки. При ошибке разбора или валидации сервис может передать модели конкретные замечания и попросить исправленный вариант. Число попыток настраивается, текущий пример конфигурации задаёт 3.

**Важно об «ограниченном структурированном выводе»:** в `config.yaml` по умолчанию стоит `structured_output_mode: prompt`. В этом режиме схема включается в текст запроса модели, а не передаётся провайдеру как обязательное ограничение JSON Schema на уровне API. Режимы `json_object` и `json_schema` тоже предусмотрены конфигурацией. Во всех случаях проект разбирает полученный JSON и применяет доменную валидацию.

**LLM не генерирует исходный код PlantUML.** Генераторы проекта преобразуют проверенные доменные модели в исходник диаграммы; затем отдельный рендерер создаёт изображение. Это отделяет содержание модели от синтаксиса визуализации, но не исключает ошибки в самой предложенной архитектуре или сценарии.

## Технологии и запуск

- Python 3.13+; доменные модели и проверки используют Pydantic v2.
- LiteLLM выполняет вызовы модели через OpenAI-совместимый endpoint.
- Репозиторий содержит пример конфигурации для LM Studio; распространённый локальный endpoint — `http://localhost:1234/v1`, API-ключ задаётся переменной окружения или файлом `.env`.
- Основные параметры генерации находятся в `config.yaml`; адрес endpoint и ключ не хранятся там.
- Режим рендеринга настраивается как `auto`, `plantuml`, `kroki` или URL собственного сервера PlantUML.
- Для локального рендеринга предусмотрен PlantUML Server в Docker, порт которого в текущем развёртывании публикуется на loopback-интерфейсе; в образ включена библиотека C4.

Пример запуска из корня репозитория:

```bash
uv run python scripts/generate_pipeline.py \
  --scenario docs/examples/social_network_chat.yaml \
  --out-dir output/presentation
```

Параметр `--scenario` обязателен. Также доступны `--out-dir`, `--diagram-server`, `--diagram-format png|svg`, `--no-diagram` и `--verbose`. Последний включает подробную диагностику и может выводить сырые ответы модели, в том числе фрагменты входных данных.

## Границы, которые нужно честно озвучивать

- Вход сейчас — YAML, не произвольный BRD/PDF/DOCX.
- Отдельного GUI нет.
- Сгенерированные архитектура, Sequence и API требуют экспертной проверки.
- Не заявлять измеренную экономию времени, процент точности, production readiness или автоматическое доказательство корректности: в этом пакете нет подтверждающих измерений.
- Локальная LLM не означает, что вся обработка локальна: режим `auto` может обращаться к публичным рендерерам. Самостоятельный локальный PlantUML Server избегает отправки исходников диаграмм публичному рендереру, но HTML Swagger UI загружает CSS/JavaScript с CDN и для этого требует интернет-доступа.
