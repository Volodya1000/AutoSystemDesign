# Сначала отчёт: пользовательский вид и машинный контракт

**Статус:** предложенный контракт, не существующая Pydantic-модель. Код и JSON Schema появляются в отдельном PR после review. Числа в макете ниже **условные**, они не получены из запуска SimPy.

## Страница 1 PDF: решение, основанное на данных

> **Имитационная проверка: checkout_baseline**  
> Эксперименты: baseline 20 RPS / peak 60 RPS; 20 повторений, фиксированные seed; моделируемое время 3600 с + прогрев 300 с в каждом повторении.  
> **Peak:** 99-я процентиль сквозной задержки = 510 мс (модельная оценка); цель = 450 мс.  
> **Статус требования:** «не подтверждено / решение зависит от статистического интервала» [пример, не вердикт].  
> Основное узкое место: `orders_db` — ожидание в очереди.  
> Ограничения: это модель, а не реальные прогоны; availability не оценивалась.

Нужны не просто таблицы: первое экранное резюме раскрывает сценарий, результат **каждого** критичного требования, наиболее важную причину задержки, покрытие модели и ограничение уверенности.

## Остальные разделы PDF

1. **Матрица требований:** идентификатор/тип NFR, оператор и порог, baseline/peak, оценка, интервал/объём выборки, вердикт, причина `inconclusive/not_evaluated`.
2. **Результат для клиента:** latency p50/p95/p99, доля неуспеха, admission rejects, completions, throughput, **незавершённые** на момент окончания эксперимента; время берётся от прихода клиентского запроса до завершения синхронного ответа.
3. **Узлы:** предложенные запросы и реально обслуженные, доля занятых сервисных каналов, средняя и максимальная очередь, *time-weighted* очередь p95, время ожидания и обслуживания, доля отказов на входе. Числа разделяются по workload phase.
4. **Причины:** топ-узлы по вкладу в задержку, перегрузке, очередям и потерям; связанные `node_identifier`, основанные на наблюдениях.
5. **Графики:** CDF задержки, динамика очередей во времени, throughput и доля незавершённых, baseline vs peak. Графики показывают агрегаты, не дорисованные точки; исходные сырые события необязательны для экспорта.
6. **Методика:** параметры распределений, seed, продолжительность прогрева, горизонт, репликации, политика остановки, доля покрытых путей, ограничения и причины неоценённых NFR.
7. **Сравнение с аналитикой (опционально):** рядом с M/M/1 или M/M/c на простых кейсах показываются обе оценки с подписью «аналитическая / имитационная» и допущениями; без смешивания в одну «истину».

**Внимание:** пример схемы демонстрирует формат, а **не согласованные числа**. Сочетание `p99=510`, `status=inconclusive` намеренно означает, что точечная оценка **сама по себе** не даёт статистического вердикта. При реализации `confidence_interval` и счётчики будут рассчитываться строго и согласовываться между собой. Для реального принятия решения необходим интервал для доли запросов, уложившихся в SLO, с учётом зависимости событий внутри прогона.

## Семантика полей

- `status` отчёта: `complete/partial/unavailable` — степень покрытия эксперимента; не статус стадии PipelineRunner.
- `requirements[].status`: `met/violated/inconclusive/not_evaluated`; не смешивать недостаточную статистику с неподдержанной моделью.
- `observed_value=null` = оценку **невозможно** или **пока нельзя** вычислить; реальный 0 остаётся 0.
- `rejected` ≠ `timed_out` ≠ `unfinished`. Любая другая терминология требует отдельного класса причины.
- `generated` учитывает только клиентские корневые запросы. Дочерние вызовы учитываются по узлам отдельно и не прибавляются к числу клиентских операций.
- `throughput` = завершённые клиентские операции / длительность **окна измерения**, с оговорённой политикой прогрева и окончания; без смешивания с входящей интенсивностью.
- Время ответа и отказы должны иметь общий знаменатель и ясную область: latency-percentile завершённых запросов не включает rejected. Рядом обязательно выводить долю отказов и censored/unfinished.
- Метрики узлов не содержат фиктивных значений для неподдержанных ветвей.
- Версионирование схемы и генерируемая JSON Schema требуют тестов совместимости, как в [аналитическом отчёте](../performance-analysis/13-e2e-and-schema.md).

## Статистическое решение об NFR

Для требования «p99 времени ответа ≤ T» эквивалентная постановка при непрерывном времени: доля **всех целевых запросов**, удовлетворяющих `latency ≤ T`, должна быть не меньше 0.99. Важно заранее определить, входят ли отказанные/незавершённые запросы в знаменатель цели; для клиентского SLO v1 **они считаются неуспехом**, а не исчезают из статистики.

Сначала считаем независимые **повторения всего эксперимента**, а не изображаем миллионы коррелированных запросов независимыми наблюдениями. Для каждой репликации фиксируем `success_fraction`; затем строим оговорённый одноcторонний доверительный интервал **по повторениям** (с проверкой достаточности повторений и явными допущениями метода).

- `met`, если нижняя граница интервала ≥ целевой доле.
- `violated`, если верхняя граница интервала < целевой доли.
- `inconclusive` иначе, в том числе при слишком малом числе независимых повторений или отсутствии обоснованного интервала.
- `not_evaluated`, если у типа требования нет корректной модели.

P99 в отчёте — описательная величина распределения завершённых запросов. Вердикт по клиентскому SLO — отдельная статистическая проверка успешной доли, а не доверительный интервал «из воздуха» вокруг p99. Метод построения интервала, размер выборки и тест покрытия для малого n фиксируются в отдельном PR.
