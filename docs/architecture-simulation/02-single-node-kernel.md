# Этап 2: минимальное ядро SimPy для одного обслуживающего узла

## Идея без формул

Пользователь заранее задаёт время прихода отдельных запросов и время их обработки.
Имитационная модель воспроизводит работу одного узла: запросы ожидают свободный
ресурс и обслуживаются по принципу **FIFO** (первым пришёл — первым обслужен).

Это первый настоящий **дискретно-событийный** расчёт AutoSystemDesign.
Он не вызывает LLM, не строит C4 и пока не рассчитывает p95/p99 либо NFR.
Результат сохраняется в типизированных объектах, которые можно использовать
для последующей агрегации и построения отчёта.

## Что происходит внутри

```text
Вход: запросы (время поступления, длительность обслуживания)
                       |
              simpy.Environment
                       |
               simpy.Resource(c)
                       |
           arrival -> wait -> service
                       |
       наблюдения (start, finish, wait)
```

Виртуальное время измеряется в **секундах**. `Resource(capacity=c)`
представляет `c` независимых каналов обслуживания. Когда все каналы
заняты, новые запросы ждут в очереди в порядке поступления.

- `ScheduledRequest.arrival_seconds`: момент поступления запроса.
- `ScheduledRequest.service_seconds`: длительность обработки после получения канала.
- `SingleNodeSimulationPlan.service_channels`: число одновременно работающих каналов.
- `CompletedRequestObservation`: фактические метки времени для отдельного запроса.
- `SingleNodeSimulationResult`: список наблюдений в порядке исходных запросов.

### Разбор примера вручную

Даны три запроса, все пришли при `t=0`; время обслуживания — `2, 1, 1` секунд.
В узле один канал:

| Запрос | Приход | Начало обслуживания | Завершение | Ожидание | Время ответа |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | 0 | 2 | 0 | 2 |
| 1 | 0 | 2 | 3 | 2 | 3 |
| 2 | 0 | 3 | 4 | 3 | 4 |

**Формулы для запроса `i`:**

```text
wait_i = start_i - arrival_i
response_i = completion_i - arrival_i
```

Где `arrival_i` — приход, `start_i` — начало обработки,
`completion_i` — завершение, все моменты измеряются в секундах.
Ожидание **не включает** время обработки.

Если увеличить число каналов до двух при сервисных временах `2, 2, 1`,
два первых запроса работают одновременно с 0 до 2 секунд, третий
ждёт до 2 секунд и завершается при 3 секундах.

## Реализация и граница зависимостей

- [kernel.py](../../src/domain/architecture_simulation/kernel.py) — Pydantic-план
  и результаты наблюдения, **без** импорта SimPy.
- [protocols.py](../../src/application/architecture_simulation/protocols.py) —
  `SimulationEngineProtocol`, описывающий метод `simulate`.
- [simpy_engine.py](../../src/infrastructure/architecture_simulation/simpy_engine.py) —
  единственный адаптер SimPy: виртуальный планировщик и `simpy.Resource`.
- [test_simpy_engine.py](../../tests/unit/architecture_simulation/test_simpy_engine.py) —
  ручные сценарии FIFO, многоканальности, прихода в свободную систему,
  независимости прогонов, нарушения контракта и пустого расписания.

### Почему генератора случайности пока нет

Расписание здесь **задано явно**, случайность не используется.
Поэтому повторный вызов при том же плане возвращает те же наблюдения
без ненужного параметра seed. На этапе 3 появятся распределения Пуассона/Gamma
и генератор случайных чисел из `SimulationConfiguration.base_seed`.

### Почему очередь пока не ограничена

`simpy.Resource` моделирует ожидание, но сам по себе не отражает
`maximum_queue_size` и `maximum_concurrency` модели C4.
Установление контрактов admission/rejection и переполнения будет сделано
на этапе 5, после согласования семантики реплик и каналов в графе.
Этот PR не заявляет, что проверяет реальные конечные очереди.

### Почему результат не является `SimulationReport`

`SingleNodeSimulationResult` хранит **события**, а не статистику по нагрузке:
нет горизонта измерения, отбрасывания прогрева, независимых повторений,
отказов или доверительных интервалов. Нельзя строить из его единичного
результата уверенный вердикт `met`. Построение агрегатов — этапы 3 и 7.

## Допущения и ограничения

1. Все запросы завершаются: `Environment.run()` обрабатывает всё расписание.
2. Одно устройство, независимые одинаковые каналы, FIFO без приоритетов и прерывания.
3. Время обслуживания и поступления задаются пользователем без случайных распределений.
4. Нет маршрутов, сети, fan-out, таймаутов, повторных попыток и потерь.
5. Порядок наблюдений соответствует **порядку входных запросов**, а не завершений.
6. `service_channels` — реальное число каналов, **не** `maximum_concurrency`.
