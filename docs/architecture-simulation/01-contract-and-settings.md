# Этап 1: контракт JSON и настройки эксперимента

## Зачем начинать с моделей, а не с SimPy

Движок будет воспроизводить миллионы виртуальных событий, но пользователь получит один
проверяемый результат. До запуска нужно договориться, что означает каждый показатель,
в каких единицах он выражен и как отличать отсутствующие данные от измеренного нуля.

Этот PR **не запускает симуляцию**. Он реализует типизированный JSON-контракт,
используемый следующим этапом при разработке ядра событий.

## Ключевые классы и файлы

- [configuration.py](../../src/domain/architecture_simulation/configuration.py): `SimulationConfiguration`, выбор распределений и горизонта.
- [report.py](../../src/domain/architecture_simulation/report.py): `SimulationReport`, `SimulationExperiment`, `RequirementEvaluation`, `LatencyQuantiles` и связанные типы.
- [root.py](../../src/config/root.py): поле `AppSettings.simulation`, загружаемое существующим **Pydantic Settings**, без создания второго загрузчика.
- [test_report.py](../../tests/unit/architecture_simulation/test_report.py): сериализация, границы, инварианты.
- [test_settings.py](../../tests/unit/architecture_simulation/test_settings.py): значения по умолчанию и переменные окружения.

## Равенство для учёта корневых запросов

Каждый **измеряемый корневой** запрос должен получить ровно один исход:

\[
N_g = N_c + N_r + N_t + N_f + N_u
\]

Здесь:

- `N_g`: `generated_requests`, число клиентских запросов, созданных в измеряемом окне;
- `N_c`: `completed_requests`, количество успешно завершившихся операций;
- `N_r`: `rejected_requests`, количество отклонений при приёме;
- `N_t`: `timed_out_requests`, количество истёкших таймаутов;
- `N_f`: `failed_requests`, количество прочих завершившихся ошибок;
- `N_u`: `unfinished_requests`, количество запросов, остающихся незавершёнными на горизонте.

**Пример:** клиент отправил 5 запросов, из них 3 успешно обработаны,
1 отвергнут заполненной очередью, 1 остался в обработке при остановке.
Тогда `5 = 3 + 1 + 0 + 0 + 1`. Если движок потерял один запрос
и выдал `5 = 3 + 1 + 0 + 0 + 0`, Pydantic отклонит отчёт.

Этот инвариант не суммирует события внутренних вызовов и fan-out:
одна клиентская операция может породить несколько внутренних событий,
но на верхнем уровне остаётся **одной** операцией.

## `null` и статистический статус

- `client_latency_milliseconds.p99 = null`: нет обоснованного процентиля для завершённых запросов.
- `p99 = 0`: зафиксирована настоящая нулевая модельная задержка, что принципиально другая информация.
- `status = inconclusive`: модель допускает оценку требования, но статистических свидетельств ещё недостаточно.
- `status = not_evaluated`: модель для данного требования неприменима (например, `availability` без отказов и восстановления).
- `met/violated` требуют хотя бы наблюдения и явно сохранённого доверительного интервала. Реальную математическую проверку границ относительно порога реализует **этап 8**, контракт сам по себе ничего не подтверждает.

Доверительный интервал хранит `lower`, `upper`, `confidence_level`, `method`.
Его границы для клиентского SLO относятся к **доле запросов, уложившихся в порог**,
а не к числу миллисекунд описательного `p99`.

## Настройки через существующий Pydantic Settings

Пример секции в корневом `config.yaml`:

```yaml
simulation:
  warmup_seconds: 300
  measurement_seconds: 3600
  replications: 20
  base_seed: 12345
  max_events_per_replication: 5000000
  arrival_process: poisson
  service_distribution: gamma_moments
  horizon_policy: stop_at_horizon
```

Для конфигурации окружением уже работает правило корневого `AppSettings`:
`ASD_SIMULATION__REPLICATIONS=7` или `ASD_SIMULATION__BASE_SEED=0`.
Параметры — типизированные значения Pydantic с ограничениями.
Новый `BaseSettings` и отдельный парсер YAML не добавляются.

## Ограничения и решения на будущее

- Предлагаемый `schema_version = 1.0` пока не сопровождается опубликованной JSON Schema.
  Её генератор и проверка CI запланированы на этапе интеграции.
- `model_version = simpy-v1` — обозначение будущей модели, а не заявление
  об уже реализованной симуляции.
- `SimulationConfiguration` — **модель параметров**, а `AppSettings` —
  единственный загрузчик источников. Библиотеки SimPy, ReportLab и время настоящего сервера
  в доменных моделях отсутствуют.
- В контракте нет «универсальной метрики»: RPS, доля загрузки, миллисекунды
  и количество ожидающих запросов ограничиваются по-разному.
- Метрики определяют форму данных, но ещё не правила сбора. Временные
  интегралы для очередей, схема warm-up и статистическая достоверность должны
  быть подтверждены отдельными тестами реализации, а не только валидацией JSON.
