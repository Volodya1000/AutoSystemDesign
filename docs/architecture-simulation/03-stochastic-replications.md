# Этап 3: случайные запросы и повторения SimPy

## От ручного расписания к нагрузке

Этап 2 задавал время прихода каждого запроса вручную. Теперь одна репликация
содержит поток случайных поступлений и обработку в одном узле с FIFO-очередью.
Это **гипотетическая модель**, а не нагрузочное тестирование системы.

**Поступления.** При интенсивности `λ` запросов/с интервалы
`A ~ Exp(λ)` со средним `E[A]=1/λ` секунд. Если `λ=0`, запросов нет.
При `λ=10` средний интервал 0,1 секунды. Интервалы не равны друг другу.

**Обработка.** Пользователь задаёт среднее `m` и отклонение `s` в секундах.
При `s=0` время постоянно и равно `m`. Иначе предположено
`S ~ Gamma(k, θ)`, где `k=(m/s)²`, `θ=s²/m`, поэтому
`E[S]=kθ=m` и `Std[S]=√k·θ=s`. При `s=m` получается
экспоненциальное обслуживание (полезно для сравнения с M/M/1).

Ни Пуассон, ни гамма-распределение не определяются автоматически по C4:
это **явные модельные предположения V1**.

## Warm-up, horizon и незавершённые запросы

При `warmup_seconds=1`, `measurement_seconds=3` прогрев идёт в
`[0, 1)`, а измеряемая когорта поступает в `[1, 4)`.
Состояние очереди после прогрева **сохраняется**. Симуляция прекращается
до обработки событий в `t=4`, не дожидаясь опустошения очереди.

Рассмотрим один канал, FIFO:

| Приход | Обслуживание | Завершение |
| ---: | ---: | ---: |
| 0 | 2 | 2 |
| 1 | 1 | 3 |
| 2 | 1 | 4 |
| 3,5 | 2 | позже 4 |

Итог измерения: 3 поступления, 1 завершённый и 2 незавершённых.
Приход в `t=0` относится к прогреву, а завершение точно в `t=4`
не входит в измерительное окно. Инвариант: `arrivals = completed + unfinished`.
Иначе на перегруженной системе легко получить обманчивый p99,
игнорирующий очередь к концу измерения.

## Независимые прогоны и бюджет

Для повтора `i` два отдельных потока `random.Random` используют
`base_seed+2*i` для поступлений и `base_seed+2*i+1` для сервиса.
Изменение service RNG не переставляет моменты прихода. Каждый запуск
создаёт новый `simpy.Environment`. Метрики разных повторов **не
сливаются** до последующего статистического этапа.

`max_events_per_replication` ограничивает число выполняемых
`Environment.step()`. Генератор расписания дополнительно прекращает
создание запросов при этом же лимите, до большой аллокации. Нарушение
вызывает `SimulationEventLimitExceeded`, а не ложный успешный отчёт.
Результат не содержит доверительных интервалов или вердиктов NFR.

## Код и команды

- Domain: `StochasticSingleNodePlan`, `SimulationWindow`,
  `WindowSimulationResult`, типы повторов.
- Application: `StochasticExperimentRunner`, два протокола.
- Infrastructure: `PoissonGammaScheduleGenerator`,
  `SimPySingleNodeEngine.simulate_window()`.
- Unit: отдельные тесты окон, воспроизводимости, распределений,
  защитных ограничений и сериализации.

```bash
uv sync --locked --all-groups
uv run pytest -m unit tests/unit/architecture_simulation
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests scripts
```
