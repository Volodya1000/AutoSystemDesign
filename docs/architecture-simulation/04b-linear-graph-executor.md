# Этап 4B: исполнение линейной C4-цепочки в SimPy

## Что добавлено

После строгого отображения C4 в
[GraphSimulationPlan](04-graph-mapping.md) теперь можно воспроизвести
**одну линейную синхронную цепочку**: Client → API → Database.
Результат `GraphTraceWindowResult` содержит время завершения
**прямого обхода**, но **не** доказывает клиентскую round-trip latency,
которая могла бы включать ответный сетевой путь.

Каждая реплика узла имеет **свой** `simpy.Resource`, число одновременно
работающих каналов берётся из `service_channels_per_replica`. Выбор
реплики происходит round-robin. Между узлами время
`network_latency_seconds` моделируется отдельным событием.

## Числовой пример без случайности

Две сетевые задержки по 4 мс, API: 50 мс сервиса, DB: 20 мс.
Первый запрос приходит при t=0. Прямой путь:

```text
0 + 0,004 (web → api)
  + 0,050 (api processing)
  + 0,004 (api → db)
  + 0,020 (db processing)
  = 0,078 секунды
```

Если в тот же момент приходит **второй** запрос, API обслуживает их
параллельно, но одноканальная DB создаёт очередь. Первый завершается
при 78 мс, второй при 98 мс. При горизонте 90 мс: поступило два,
завершён один, незавершён один. Все эти числа проверяет unit-тест.

## Что принципиально ещё не учитывается

1. **Очередь без ограничения** на этом экспериментальном этапе,
   даже если в C4 указан конечный `maximum_queue_size`. В результате
   явно записан `queue_model: unbounded_prototype`. Admission и
   отказы из-за заполнения появятся на этапе 5.
2. **Никакого fan-out и альтернативных маршрутов.** Такой граф
   отклоняется до исполнения с типизированной причиной, а не
   имитируется неправильной последовательностью.
3. **Cache hit/miss не сводится к обслуживанию cache как сервера.**
   Если кэш входит в маршрут, исполнение пока отклоняется.
4. Обрабатывается только **переданная последовательность приходов**.
   Случайные потоки этапа 3 будут подключены к полноценному graph-runner,
   когда определены admission и маршрутизация.
5. Не поддерживаются retry и async. Нет доверительных интервалов и
   NFR-вердиктов, нет JSON/PDF интеграции с конвейером.

Сервисное время в узлах постоянно при `s=0`, иначе используется
Gamma с теми же моментами, что и на этапе 3. Для отдельного узла
источник случайности зависит от `seed` и идентификатора узла, поэтому
перестановка массива `resources` не меняет результат. Входная
очередь и SimPy environment создаются заново для каждого запуска.

```bash
uv run pytest -m unit tests/unit/architecture_simulation/test_linear_graph_engine.py

```
