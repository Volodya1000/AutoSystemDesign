# Имитационная проверка архитектуры: SimPy

**Статус: проектирование, реализации пока нет.** Эта папка описывает новую, отдельную от аналитического анализа производительности фичу AutoSystemDesign.

## Начать с результата

Представьте, что AutoSystemDesign построил граф C4 для сервиса оформления заказов. Пользователь хочет ответ не «архитектура выглядит правдоподобно», а:

- выдержит ли **модель** заданную входную нагрузку и где именно образуется очередь;
- какую долю запросов модель завершает в пределах целевого времени, каковы p50/p95/p99;
- какие узлы перегружены, сколько задач потеряно из-за заполненных буферов;
- как изменится картина при увеличении реплик или потока запросов;
- какие нефункциональные требования удалось проверить, какие нарушены, а какие **нельзя оценить** по доступным данным.

Результат: канонический JSON `<scenario>_simulation.json` и опциональный, хорошо читаемый PDF `<scenario>_simulation.pdf`. Две репрезентации одного расчёта, не два конкурирующих источника истины.

**Это моделирование гипотетической архитектуры, а не нагрузочное тестирование реальных сервисов.** Обязательно показываются входные допущения, seed, длительность прогона, число независимых повторений, статистическая неопределённость и покрытие требований.

## Архитектурные границы

| Слой | Планируемое назначение |
| --- | --- |
| `domain/architecture_simulation/` | Типизированные параметры модели, результаты и чистая оценка требований |
| `application/architecture_simulation/` | Запуск повторений, агрегация статистики и построение JSON-отчёта |
| `infrastructure/architecture_simulation/` | Адаптер SimPy, генераторы событий и специализированный PDF |
| `application/pipeline/stages/` | `ArchitectureSimulationStage`, зависящая от `StageId.C4` |
| `infrastructure/reporting/pdf/` | Только действительно общие компоненты двух ReportLab-рендереров, после появления второго |
| `tests/unit/architecture_simulation/` | Быстрые фиксированные примеры, границы и статистика |
| `tests/integration/architecture_simulation/` | Настоящий PipelineRunner/файлы и независимые прогоны без LLM |

Это **предлагаемые** пути, а не уже добавленные пакеты. Не создавать папки и абстракции ради вида.

## Основные решения

- Исходные модели C4 и требования не дублируются в новом YAML «для симулятора». При необходимости к ним добавляются строго типизированные параметры эксперимента.
- Две независимые ветки анализа читают граф C4; симуляция не считывает округлённые значения из аналитического PDF/JSON.
- Для одного и того же input + версии модели + seed воспроизводимы результаты; недетерминированное реальное время выполнения не включается в сравнительные метрики.
- `null`, `not_evaluated` и `inconclusive` имеют разные смыслы. Нельзя превращать неопределённость в положительный вердикт.
- Изменения требуют документа, независимого числового примера, unit-тестов и обновления [индекса PR](PR_INDEX.md).
