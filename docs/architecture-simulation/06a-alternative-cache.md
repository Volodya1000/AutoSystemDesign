# Этап 6A: альтернативные маршруты и cache hit/miss

## Один клиентский запрос — один выбранный путь

Если у сервиса несколько исходящих связей с `routing_mode=alternative`,
один запрос выбирает **ровно одну** из них. Пока веса не поддерживаются,
все альтернативы равновероятны. Например:
`web → API → {DB_A | DB_B}`.

Выбор зависит от seed, номера корневого запроса и идентификатора
источника. Перестановка элементов `edges` не меняет результаты.

## Канонический cache fallback в C4

В исходном `ArchitectureGraph` кэш **не вызывает БД**. Читатель
выполняет lookup, а при промахе сам вызывает БД. Поэтому обязательны
два **физических ребра из compute**:

```text
web → API ── lookup ──→ Cache
         └── miss ────→ DB
```

- `API → Cache`: каждый выбранный lookup, как при hit, так и при miss.
- `API → DB`: **только** если lookup завершился промахом.
- `Cache → DB`: запрещено структурными правилами C4; SimPy не требует
  и не создаёт такого физического ребра.
- Оба исходящих ребра не являются двумя независимыми альтернативами:
  DB — условное продолжение **того же** корневого запроса.

В SimPy при miss последовательность **событий** выглядит как
`API, Cache, DB`, но задержка перехода к DB берётся с ребра
`API → DB`. Это последовательность обслуживания одного запроса,
а не новая связь в C4. При попадании запрос заканчивает прямой
маршрут после Cache.

### Числовой пример

Время обслуживания API = 50 мс, Cache = 3 мс, DB = 20 мс.
Сетевая задержка каждого ребра = 4 мс.

- Hit: `4 + 50 + 4 + 3 = 61 мс`.
- Miss: `61 + 4 + 20 = 85 мс`.

Обратный путь ответа, дополнительный hop Cache → API и клиентский
round-trip **не моделируются**; нельзя объявлять эти 61/85 мс полноценной
клиентской латентностью.

### Согласование с аналитикой

Для потока запросов с интенсивностью `λ` и hit rate `h`:

```text
λ_Cache = λ_lookup
λ_DB    = λ_lookup × (1 - h)
```

При `h = 1` обращений к DB нет, при `h = 0` каждый lookup
приводит к одному обращению в DB. При `0 < h < 1` SimPy
проводит независимый seeded-выбор на запрос; эмпирические доли
приближаются к теоретическим, но не обязаны совпадать в малой выборке.

При нескольких compute-читателях одного cache каждый читатель должен
иметь собственное исходящее ребро к DB. После промаха используется
fallback **того же читателя**, а не случайное DB-ребро другого
читателя. Один compute, читающий несколько cache, отклоняется как
неоднозначный контракт.

Если у читателя несколько DB-fallback с `alternative`,
промах равновероятно выбирает один; аналитический поток делится
между ними. Если у него есть другие обычные альтернативы,
выбор между ними и cache происходит до hit/miss; DB-fallback
не участвует в этом первичном выборе.

## Явные границы прототипа

- Нет синхронного `fan_out`/join, включая несколько DB-fallback
  с fan-out: такой граф отклоняется, а не трактуется как alternative.
- Нет моделирования timeout/retry, async, round-trip и NFR-вердиктов.
- Отсутствие DB-fallback, несколько cache от одного compute,
  вход в cache не от compute и физический исходящий edge cache
  приводят к типизированной ошибке `invalid_cache_topology`.
- Несовместимые routing modes не приводят к молчаливому
  переопределению потока.

Тесты проверяют единую топологию через `StructuralTopologyValidator`,
`CacheUsageValidator`, `compute_node_incoming_rps`,
`ArchitectureSimulationPlanMapper` и реальный `SimPyLinearGraphEngine`.
Так отдельно контролируются C4-инварианты, ожидаемые RPS и
наблюдаемые посещения узлов.

```bash
uv run pytest -m unit tests/unit/architecture_simulation
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests scripts
```
