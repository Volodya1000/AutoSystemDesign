# Техническое задание: дискретно-событийная симуляция C4-графа

## Проблема и полезный результат

Существующая аналитическая фича оценивает средние величины и риски очередей при определённых предположениях. Её задача не состоит в получении эмпирических распределений времени ответа. Новая фича должна **разыгрывать отдельные запросы во времени**: поступление, маршрутизацию, ожидание ресурса, обработку, переполнение очереди и завершение клиентской операции.

Целевая аудитория: разработчик или системный архитектор, который сравнивает кандидаты архитектуры **до закупки инфраструктуры и нагрузочных испытаний**. Главное преимущество: не одно «зелёное число», а объяснимая связь `требование → параметры графа → моделируемые события → наблюдения → уверенность в выводе`.

## Пользовательские истории

- Как архитектор, я задаю сценарий нагрузки и граф, запускаю воспроизводимый эксперимент и вижу, какие задержки возникают у **завершённых** запросов, сколько запросов не было обслужено и почему.
- Как инженер, я вижу p50/p95/p99 **сквозного** клиентского времени и распределения ожидания для узлов, а не пытаюсь вычислить p99 сложением средних.
- Как автор требований, я вижу `met / violated / inconclusive / not_evaluated` для **каждого** поддержанного NFR, с числовым свидетельством и причиной отсутствия решения.
- Как инженер по производительности, я могу задать одинаковый эксперимент для двух вариантов числа реплик, сравнить относительные изменения и увидеть интервал неопределённости, не называя модельные цифры реальными измерениями.
- Как пользователь CLI, я получаю структурированный JSON даже при ограничениях входного графа; необязательный PDF может не создаться без потери данных.

## Функциональные требования первой версии

| ID | Условие | Критерий результата |
| --- | --- | --- |
| F-01 | C4-граф и DesignScenario доступны | Отдельная стадия после C4, без нового LLM-вызова |
| F-02 | Заданы время эксперимента, прогрев, повторения, seed и режим нагрузки | Валидируемый, сериализуемый конфиг с явными единицами |
| F-03 | Для известных параметров обслуживания построены ресурсы узлов | Учитываются явные каналы, реплики и ограничения очереди, без подстановки числа каналов из concurrency |
| F-04 | Запросы идут через поддерживаемые синхронные связи | Время ожидания, обработки и сети фиксируется на уровне событий |
| F-05 | Очереди переполняются | Отдельно учитываются admission reject, timeout/cancel (если реализованы), незавершённые к концу окна; это разные причины |
| F-06 | Повторено несколько независимых запусков | P50/p95/p99, throughput, utilization, time-weighted queue size, потерянные запросы и доверительные оценки |
| F-07 | В сценарии есть требования | Для поддерживаемого latency percentile/SLO построено честное решение; для неподдержанных NFR выдан `not_evaluated` |
| F-08 | Результат построен | JSON по Pydantic-контракту, опциональный PDF без новых вычислений |
| F-09 | На входе нет workload или неизвестна семантика обязательного участка графа | Отчёт помечает неполноту, не придумывает числа |
| F-10 | Повторный запуск с одинаковыми параметрами | Совпадают исходные данные, метрики и их порядок с оговорённой точностью |

## Нефункциональные требования к самому симулятору

1. **Воспроизводимость:** все стохастические решения получают RNG из известных seed каждого независимого повторения; порядок узлов/рёбер в JSON не влияет на результаты.
2. **Изоляция:** unit/fixture integration без сети, LLM, PlantUML, wall-clock sleeps и PDF-сервера; SimPy работает в виртуальном времени.
3. **Ограниченность:** лимит числа событий/наблюдений и явный статус прекращения вместо бесконечного моделирования перегрузки.
4. **Наблюдаемость:** ошибки конфигурации отделяются от недостаточной статистики, от модели с ограниченным покрытием и от ошибки записи.
5. **Согласованность артефактов:** PDF выводит только данные канонического JSON; правило «PDF необязателен, JSON обязателен» сохраняется.
6. **Стиль:** Python 3.13; Pydantic Settings для конфигурации, строгое типизирование, разделение domain/application/infrastructure, SOLID/KISS/DRY; новые правила линтера не отключать ради фичи.

## Область V1 и честные ограничения

- Входы: `ArchitectureGraph`, `DesignScenario`, отдельный config симуляции. **Baseline** и **peak** запускаются как **два отдельных стационарных** эксперимента, а не как выдуманный временной burst.
- Первая расчётная версия: пуассоновские поступления, сервисное время с явно документированным распределением, синхронная цепочка; fan-out и cache fallback добавляются отдельными PR после определения корреляции запросов и join.
- Для очереди с ограниченной вместимостью результат зависит от явно выбранной политики отказа при заполнении; до её реализации никаких оценок потерь.
- `maximum_concurrency` не означает `service_channels_per_replica`. Если каналов нет, соответствующая ветвь не симулируется с выдуманной мощностью.
- Режимы `alternative`, `fan_out`, cache hit/miss и `is_asynchronous` уже существуют, но требуют событийной семантики; нельзя просто воспроизвести ожидаемый RPS как независимые клиентские транзакции на каждом узле.
- Retries, timeouts, асинхронная доставка, распределённые блокировки, сетевые отказы, восстановление, база с репликацией и зависимые от размера сообщения времена обслуживания входят в дальнейшие этапы **только после появления входных данных и однозначного контракта**.
- `availability` в текущем YAML измеряется процентом доступности сервиса, но **нет** параметров отказов и восстановления. Процент успешных транзакций в SimPy не является availability: статус `not_evaluated`. `budget` относится к другому валидатору; `queue_size_percentile` и `resource_utilization` проверяются только после выбора объекта измерения и окна.
- Сравнение с реальным железом и автоматическая модификация архитектуры не входят в V1.

## Показатель полезности

Вместо маркетингового «проверили 99.99% надёжности» фича должна давать **трассируемое свидетельство**. Пользователь должен понимать, где задержка (очередь или обработка), какую часть требований можно было проверить и какое изменение архитектуры имеет смысл **испытать** следующим. Рекомендации порождаются детерминированными правилами, а не LLM.
