# Финальная приёмка корневого PR: SimPy-проверка C4

**Статус: чек-лист подготовлен заранее, пункты не считаются пройденными.** Отметки проставляются только по фактическому логу с конечным SHA и сохранёнными артефактами. До завершения предшествующего [PR #90](https://github.com/Volodya1000/AutoSystemDesign/pull/90) и согласования модели никакой merge новой фичи в `master`.

## A. Архитектурные блокеры

- [ ] Все дочерние PR интегрированы в root feature-ветку и видны в `git diff`; номера занесены в [PR_INDEX.md](PR_INDEX.md).
- [ ] C4 остаётся единственным источником узлов/рёбер. Симуляция не дублирует формат архитектуры и не делает LLM-вызов.
- [ ] Domain/application не импортируют SimPy или ReportLab; их инфраструктурные адаптеры подключаются в composition root.
- [ ] Стадии используют типизированный `StageId` и корректный `depends_on=(StageId.C4,)`. Runner остаётся последовательным, если нет отдельного доказанного основания его менять.
- [ ] Pydantic Models/Pydantic Settings, Python 3.13, uv.lock; статический анализ, единицы измерения и JSON Schema в согласии с CI.
- [ ] Проверено, что `maximum_concurrency` не подменяет количество каналов; fan-out не умножает число **клиентских** запросов.
- [ ] PDF-общие компоненты вынесены по фактическому дублированию; старый performance-PDF проходит исходные регрессии.

## B. Контракт JSON и PDF

- [ ] `SimulationReport` выполняет round-trip, запрещает неизвестные поля, NaN, Infinity и отрицательные время/счётчики, когда они невозможны.
- [ ] Опубликованная `report.schema.json` генерируется из Pydantic и проверяется на актуальность без перезаписи в CI.
- [ ] `null` не превращается в 0, `not_evaluated` — не в `met`, отсутствие данных — не в сообщение об успехе.
- [ ] Каждый эксперимент сохраняет seed, время прогона, число повторений, версию модели, режим нагрузки, дистрибутивные допущения и статистический метод.
- [ ] Результат baseline не перезаписывается peak; оба представлены отдельно.
- [ ] PDF выводит значения **из JSON DTO**, не пересчитывает p99, доли потерь или verdict.
- [ ] PDF: русские строки доступны для поиска, таблицы читаемы, страницы и переносы не обрезают значения; тест машинного извлечения **и** ручной просмотр.
- [ ] Нет системного Unicode TTF → объяснённый warning, JSON сохранён, стадия PARTIAL; ошибка обязательного JSON даёт FAILED.
- [ ] Предупреждения о смоделированных, а не реальных метриках и неподдержанной availability есть в обоих форматах.

## C. Числовые и статистические эталоны

| Случай | Ожидаемое проверяемое свойство | Недопустимо |
| --- | --- | --- |
| Один узел, нулевая дисперсия и нулевая очередь | Обслуживание равно заданной длительности; при пустом ресурсе нет искусственного ожидания | Случайные задержки при s=0 |
| M/M/1 λ=10, μ=20 | ρ=0.5, Wq=50 мс, W=100 мс **в математической модели**; оценка длинного прогона приближается с измеренной неопределённостью | `assert simulated_mean == 100` для конечной выборки |
| M/M/c λ=10, μ=20, c=2 | Эрланг C P(wait)=0.1; Wq≈3.33 мс; W≈53.33 мс | Отождествление c с max concurrency |
| Полная очередь size=0 | Когда все каналы заняты, новая заявка отвергается | Запрос молча пропадает или обслуживается сверх capacity |
| Перегрузка λ=30, μ=20 | При ограниченной очереди появляются отказы; незавершённые считаются отдельно | Бесконечная симуляция или выдуманный стационарный W |
| Alternative 2 направления | Каждый корневой запрос попадает **в одну** из ветвей | Два клиента из одного запроса |
| Fan-out 2 синхронных ветви | Каждая получает дочернее событие; клиент ждёт нужный join | Сложение средних или независимая генерация клиентов |
| Cache hit rate 100% / 0% | 100% не обращается к DB fallback; 0% идёт к fallback | Двойные DB события |
| Перемешанный порядок графа | При тех же seed совпадают отсортированные артефакты | Изменение результата от порядка списка |
| Отсутствующие каналы или workload | `partial/unavailable` и стабильная reason code | Выдуманный канал или пропускная способность |
| Одна репликация / мало событий | `inconclusive` для статистически неподтверждённого percentile-SLO | Уверенный `met` по точечной p99 |
| Неподдержанная availability | `not_evaluated`, описан missing failure/repair model | `met` из 0% rejects |
| Два независимых прогона | Отдельные каталоги, seed, корректные числа | Потеря данных из-за общего mutable state |

### Статистическая дисциплина

- [ ] Моделирование проверено на фиксированных трассах без случайности (порядок событий, очереди, join, потери).
- [ ] Длинный stochastic suite сравнивается с аналитическим эталоном с **заранее согласованным** статистическим допуском/интервалом; нельзя после неудачи расширять допуск, пока тест не станет зелёным.
- [ ] Проверена реплицируемость при одинаковой версии Python/SimPy и seed, включая независимость потоков случайных чисел между повторениями.
- [ ] Сохранена политика окна, прогрева, drain/censored; нет случаев, когда completed + rejected + unfinished не согласуется с generated для корректно определённой когорты.
- [ ] Метод односторонних доверительных границ для SLO указан в JSON; метод признаёт корреляцию внутри прогона.
- [ ] Для статистически неоднозначного результата выводится `inconclusive`, а не `met`. Проверяются пограничные случаи порога.
- [ ] `mean_queue_length` вычисляется с длительностями состояний; контрольный trace позволяет руками вычислить интеграл (\int Q(t) dt).
- [ ] Ограничение по максимальному числу событий/времени прогона завершает эксперимент с понятной диагностикой, не создаёт неверного успешного отчёта.

## D. Интеграция и ручные YAML

Нужны **два типа** E2E: фиксированный C4-граф для точной проверки событий/отчётов и реальный LLM для проверки извлечения корректного C4. Второй **не** заменяет первый.

| Сценарий | Цель | Особая проверка |
| --- | --- | --- |
| `checkout_baseline.yaml` | Сквозной sync путь + клиентский latency p99 | p99 из simulated trace, не из аналитического среднего |
| `catalog_read_heavy.yaml` | Cache hit/miss и нагрузка базы | DB fallback только при промахе и явно объяснённая доля |
| `notifications_spiky.yaml` | Пиковая нагрузка и async-путь | peak как стационарный сценарий, **не** воображаемый burst; async-delivery не подмешивается в client latency |
| `helpdesk_no_workload.yaml` | Неполные исходные данные | обязательный JSON `unavailable`, понятный missing workload reason |

- [ ] Все четыре YAML валидируются актуальной Pydantic-моделью.
- [ ] Прогон в настоящем Runner с заменённой **только** C4 LLM-стадией пишет JSON и PDF с корректными связанными идентификаторами.
- [ ] Четыре реальных прогона с LLM проанализированы по логам и фактическому графу. Нет ложных PASS на unsupported semantics.
- [ ] Второй прогон той же схемы с теми же seed повторяет JSON-значения, а выходные директории не смешиваются.
- [ ] CI успешно выполнен на **окончательном head SHA** root PR после интеграции всех дочерних изменений и синхронизации с `master`.

## E. Что передавать на ручное ревью

Для каждого прогона нужны: номер PR и SHA head/base; команда, Python/SimPy версии и seed; YAML и сохранённый C4 JSON; JSON/PDF симуляции; полный stage log со статусами и предупреждениями; exit code, ссылки на все CI jobs. **Не** прикладывать `.env`, токены, секреты.

| Итог | Когда ставим |
| --- | --- |
| **GO** | Все блокирующие проверки пройдены на финальном SHA, статистические выводы обоснованы, PDF визуально проверен |
| **GO WITH MODEL LIMITATIONS** | Поддержанные части валидны, неподдержанные NFR явно `not_evaluated`; приёмка ограничивается заявленным scope |
| **NO-GO** | Ложное выполнение SLO, потерянные события, CI red, сломанный JSON, подмена отсутствующих данных нулями |
| **INCONCLUSIVE** | Недостаточные логи/артефакты или нет независимой числовой проверки; решение о merge не принято |

**Ни один пункт выше не отмечен как уже выполненный.** Документация не является реализацией.
