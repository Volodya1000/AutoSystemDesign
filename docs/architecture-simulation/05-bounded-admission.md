# Этап 5: ограниченные очереди и отказы

## Почему нельзя использовать бесконечную очередь

В прототипе линейного C4-графа любой запрос ожидал столько,
сколько потребуется. Реальная архитектура имеет конечные лимиты.
Без них перегрузка выглядела как бесконечная задержка вместо отказов.

Для каждой **реплики** теперь моделируются независимо:

- `service_channels_per_replica = c` реальных каналов обслуживания;
- `maximum_queue_size = q` ожидающих запросов, не включая работающие;
- `maximum_concurrency = k` максимальное число допущенных
  (обслуживаемые + стоящие в очереди). Это **не** число каналов.

Запрос отклоняется, если `running + waiting >= k` с причиной
`concurrency_limit`, или если заняты все каналы и очередь содержит
`q` запросов, с причиной `queue_full`. Лимит не увеличивает
число каналов. Решение происходит после моделируемой сети при входе
в соответствующий узел, а не при поступлении в клиент.

## Пример с ручной проверкой

Цепочка Client → API → DB. У DB один канал обслуживания,
20 мс на запрос. Два клиента пришли одновременно при `t=0`;
оба проходят двухканальный API за 50 мс и 4 мс сетевой задержки
до и после API.

Если у DB `maximum_queue_size=0`, запрос №0 обслуживается с
58 до 78 мс, запрос №1 в момент 58 мс получает `queue_full`.
Итог окна: `measured=2, completed=1, rejected=1, unfinished=0`.

Если очередь DB вмещает одного ожидающего: два запроса завершатся
в 78 и 98 мс. Третий одновременный клиент получит `queue_full`.

Если `maximum_concurrency=1`, а очередь больше нуля, второй
запрос получает `concurrency_limit`, хотя формально место
в `maximum_queue_size` ещё имеется. Различие проверяется тестами.

## Учёт клиентских запросов

Каждый измеряемый корневой запрос относится ровно к одному исходу:

```text
measured_arrivals = completed + rejected + unfinished
```

`GraphRequestRejection` хранит индекс клиентского запроса,
узел, индекс реплики, виртуальное время и типизированный код причины.
При отказе на любом внутреннем узле оставшаяся часть маршрута не
исполняется. Отказавший внутренний запрос **не** создаёт
дополнительного клиентского обращения. Запросы периода прогрева
продолжают занимать мощности, но не входят в измеряемую когорту.

## Ограничения

В этом этапе ещё **нет** retry policy, cache hit/miss, fan-out,
альтернативных маршрутов, асинхронной доставки, статистических
доверительных интервалов или NFR. Очередь на каждой реплике FIFO,
реплики выбираются round-robin. Модель пока измеряет прямой обход
узлов, не клиентский round-trip. Это отдельная вертикаль, которую
нельзя считать подтверждённой SLO по одному прогону.
