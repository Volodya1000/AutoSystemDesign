# ROADMAP: каскад PR для имитационной проверки C4 на SimPy

**Статус на 22 октября 2026:** этапы 0–5 и 6A реализованы в корневой feature-ветке #114. Этапы 6B–11 ещё не реализованы; финальный PR остаётся Draft. Источник истины для порядка работы.

**База:** `master`. Аналитическая фича [#90](https://github.com/Volodya1000/AutoSystemDesign/pull/90) уже объединена. Корневой PR #114 собирает этапы SimPy; дочерние этапы интегрируются в него, а не отдельно в `master`.

**Стратегия:** сначала конечный отчёт и значения, затем минимальная математически проверяемая симуляция, после этого связка с графом, статистика, вердикты NFR и только затем PDF. Каждый PR мал, имеет отдельные unit-тесты, числовой пример и образовательный .md. После очередного PR сначала обновляется [PR_INDEX.md](PR_INDEX.md), потом запускаются тесты и публикуется ссылка на проверенную ветку.

## Пользовательский результат (Definition of Done)

Пользователь запускает привычный сценарий AutoSystemDesign и получает:
1. JSON `<scenario>_simulation.json` с версией, входами, параметрами симуляции, baseline/peak, метриками клиента и узлов, количествами отказов, NFR-вердиктами и допущениями.
2. PDF `<scenario>_simulation.pdf`: понятное резюме, матрица NFR, таблица bottleneck, сравнительные графики, методика и предупреждения.
3. Внятный исход для каждого NFR: `met/violated/inconclusive/not_evaluated`, статистическая процедура и точные причины недоступности проверки.
4. Воспроизводимый результат из сохранённого C4 и конфигурации без обращения к LLM.
5. Отсутствие ложных claims про реальную эксплуатацию и availability.

Документ результата: [REPORT_CONTRACT.md](REPORT_CONTRACT.md). Ограничения и модель: [MODEL_SEMANTICS.md](MODEL_SEMANTICS.md). Матрица финальной проверки: [ROOT_PR_ACCEPTANCE.md](ROOT_PR_ACCEPTANCE.md).

**Acceptance:** ни один существенный пользовательский вывод не требует неописанной модели; каждый будущий файл имеет понятный слой.

### PR 1–3: первая вертикаль

- Pydantic-контракт разделяет `null`, `unavailable`, `partial` и `inconclusive`, имеет `schema_version`.
- Все настройки прогонов имеют явные единицы; конфигурация не передаётся списком неименованных аргументов.
- Первый расчёт использует настоящий `simpy.Environment`, без LLM и инфраструктурных измерений.
- Тесты на `s=0`, `s=m`, пустую нагрузку/недопустимый seed, прерывание по event limit.
- Нельзя выдавать один прогон за доверительный интервал.

### PR 4–6: смысл графа

- Перестановка порядка узлов/рёбер не меняет модельный результат с теми же seed.
- `service_channels_per_replica=None` **не** заменяется значением `maximum_concurrency`.
- `alternative` выбирает ровно один маршрут, `fan_out` создаёт дочерние вызовы с требуемой синхронизацией, cache miss не дублирует все DB-запросы.
- Корневые и внутренние запросы считаются отдельно; bounded queue и причины отказа оформлены типизированно.
- Для неподдержанного async/retry графа отчёт объясняет **точную** границу оценённой части.

### PR 7–8: статистика и решение

- `Q(t)` и utilization интегрируются по времени; percentile времени ответа берётся по определённой когорте.
- Подсчёт SLO success учитывает rejected и unfinished, не скрывает их из знаменателя.
- Доверительная процедура использует независимые прогоны, а не выдуманную независимость отдельных запросов.
- `met`/ `violated` объявляются лишь при статистическом отделении от порога; иначе `inconclusive`.
- `availability` остаётся `not_evaluated` до модели отказов.
- Findings детерминированно привязаны к узлам; рекомендация не выдумывает нерассчитанную экономию.

### PR 9–10: артефакты и архитектура

- Симуляционная стадия зависит **только** от C4 и scenario, не от Sequence/API или JSON аналитического отчёта.
- Stage `SUCCEEDED/PARTIAL/FAILED` отделён от статуса покрытия самого SimulationReport.
- Обязательный JSON пишется до необязательного PDF; сбой рендера не теряет JSON.
- При появлении **второго** ReportLab-рендерера выделить общий ресурс: регистрацию Unicode TTF, палитру, базовые стили, футер, оформление таблиц и условное форматирование. **Не** переносить специфичное содержание performance PDF в `BaseReportRenderer`.
- Рассмотреть узкий универсальный `PdfReportRendererProtocol[ReportT]` только при реальном дублировании точек инъекции. Конкретные рендереры остаются `PerformanceReportPdfRenderer` и `SimulationReportPdfRenderer`. Общий пакет лучше назвать `infrastructure/reporting/pdf/`, а не размыто `utils/`.
- Оба PDF должны быть читаемы и сохранять кириллицу; не коммитить бинарные шрифты.

### PR 11: root merge checklist

- Настоящий `PipelineRunner` с заменённым **только** LLM-выводом C4 выполняет полный цикл в временной директории.
- Проверки статистики M/M/1 и M/M/c делаются отдельно от screenshot/PDF тестов и допускают стохастическую погрешность.
- Все пять существующих CI на конечном SHA (включая pinned Python 3.13 и uv lock), плюс интеграционные проверки.
- Реальные четыре YAML запускаются только после устойчивой offline-приёмки. Утверждения про SLO проверяются вручную.

## Тестовая политика

Каждому PR соответствует минимальный TDD-цикл: **ожидаемое поведение → падающий тест → минимальная реализация → числовое сравнение → документация → полный CI**. Для stochastic tests: фиксированные seed и достаточный горизонт, без «точного equality» по случайным оценкам; для regression сохранённых метрик по seed допустимо сравнивать полностью при одинаковой версии Python/SimPy.

**Быстрый CI:** небольшие детерминированные примеры + property/invariant checks + fixture-интеграции; не тысячи минут виртуального времени с миллионами событий для каждого теста. **Отдельный статистический suite:** длинные независимые повторы, convergence/coverage и аналитические benchmark-числа.

## Решения до старта реализации

1. Как `maximum_concurrency` относится к очереди: admission total или активная работа?
2. Что значит sync fan-out без явного join и как идентифицировать **клиентскую** транзакцию?
3. Каков scope `latency` NFR, если в сценарии несколько функциональных операций?
4. Какая политика после horizon: обрыв с учётом unfinished или ограниченный drain?
5. Какой метод и минимальный объём независимых повторов достаточен для `met/violated`?
6. Поддерживается ли mixed graph частично или применяется `not_evaluated` ко всему клиентскому пути?

Ответы сначала записываются в [MODEL_SEMANTICS.md](MODEL_SEMANTICS.md) и [REPORT_CONTRACT.md](REPORT_CONTRACT.md), затем используются для кода.

## Порядок объединения

Отдельный **root feature-PR** аккумулирует малые дочерние PR. Исторический опыт #90/#113 показал: `Merged` дочерней ветки **не** означает, что её код попал в `master` или даже root PR. Перед финальным merge проверяются содержимое root head, опубликованная схема, логи CI на конкретном SHA и визуальная приёмка PDF. Не сливать документационный PR автоматически в `master` как завершённую реализацию.
