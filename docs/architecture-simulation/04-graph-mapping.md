# Этап 4A: перевод C4 в строгий план симуляции

## Зачем отдельное отображение

Генеративная модель создаёт `ArchitectureGraph`. В нём уже есть узлы,
рёбра, реплики, сетевые задержки, concurrency, очереди и иногда число
независимых каналов. Но эти значения **нельзя напрямую отдавать в SimPy**:
например, `maximum_concurrency=100` не означает, что сервер
обслуживает 100 запросов одновременно.

`ArchitectureSimulationPlanMapper` принимает существующие
`ArchitectureGraph` и `DesignScenario`, без повторного вызова LLM.
Результат: типизированный `GraphSimulationPlan`, пригодный для
следующего движка графа, но пока **не** новая имитация целого маршрута.

## Пример

В C4-сценарии:

```text
web (client) --4ms--> api (3 replicas x 2 channels)
                     --4ms--> db (1 channel)
```

У API отдельно хранятся `maximum_concurrency=10`,
`maximum_queue_size=20`, `service_channels_per_replica=2` и
`replicas_count=3`. Число каналов на реплику остаётся **2**, а не
становится 10 или 20. Среднее время сервиса 50 мс превращается в
0,05 с, задержка связи 4 мс в 0,004 с. Клиент не получает свою очередь.

Отсутствие `service_channels_per_replica` приводит к отказу
`service_channels_unknown`, а не к выдумыванию значения. Отсутствующий
`workload` также нельзя заменить случайной частотой запросов.

## Проверка ограничений

Преобразователь не пропускает дубли узлов/рёбер, неизвестные endpoints,
циклы, недостижимые узлы, несколько клиентских корней. Async и
повторные попытки пока не имеют определения исполнения и отклоняются
с **типизированным кодом причины**.

Для каждой связи сохраняются `routing_mode`, network latency и timeout.
Fan-out и `alternative` в этом PR только **отображаются**, но не
запускаются в SimPy. Политика выбора маршрута и синхронизации ветвей
будет реализована отдельно по ROADMAP. Не выдавать карту за
доказательство end-to-end latency.

Порядок обхода узлов определяется детерминированно. Перестановка
исходных списков `nodes` и `edges` не меняет план.
