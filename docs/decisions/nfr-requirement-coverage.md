# ADR: доказуемость нефункциональных требований и идентичность проверок

## Контекст

Issue #116: диспетчер раньше пропускал требования без валидатора. Успешная
генерация топологии ошибочно воспринималась как выполнение всех NFR.
PR #90 уже строит отдельный отчёт о производительности, но не проверяет
процентильные SLA и не должен пересчитываться здесь.

## Решение: строгая привязка, а не нечёткий поиск сущностей

Каждое требование получает адрес `requirements[0]`, `requirements[1]` и т. д.
Это **идентификатор в пределах версии сценария**, а не постоянный UUID:
перестановка списка меняет адрес. Именно адрес, дополненный
`type_identifier`, сопоставляет проверку с исходным требованием.
Два `budget` с разными порогами остаются двумя независимыми проверками.
Одинаковое название узла, сходство текста или LLM не считаются доказательством.

Диспетчер сопоставляет **точный класс** требования с зарегистрированным
валидатором. Валидатор возвращает существующие доменные ошибки; на их
основании формируются `satisfied` и `violated`. При отсутствии
валидатора результат **обязательно** `not_evaluated`, но не ошибка
ремонтного цикла LLM. Сервис сохраняет проверки в `ValidationResult`,
не теряя их при объединении структурных и сценарных проверок.

В C4 формируется отдельный `<scenario>_nfr_coverage.json`, в том числе
при неудачной генерации, если сценарий содержит NFR. При отказе парсинга
невозможно оценить требования; при структурно непринятом графе прежний
`satisfied` заменяется на `not_evaluated`: частичная проверка
отвергнутой архитектуры не доказывает её корректность. Нарушения остаются
диагностикой кандидата. `graph_accepted` отделяет оценку требований
от успешности генерации. `status=incomplete` не проваливает весь
конвейер; путь к отчёту и число непроверенных требований появляются
в предупреждениях C4.

### Матрица покрытия (v1)

| `type_identifier` | Источник доказательства | Необходимые данные | Текущее решение |
| --- | --- | --- | --- |
| `budget` | `BudgetRequirementValidator` | Стоимость узлов C4, правило сравнения | `satisfied` / `violated` |
| `latency` | PR #90: средняя задержка, **не p95/p99** | workload, распределение полной задержки | `not_evaluated`; `percentile_unmodeled` |
| `queue_size_percentile` | PR #90: оценки среднего ожидания, **не длины очереди pXX** | workload, вероятностная модель очереди и буфера | `not_evaluated`; `percentile_unmodeled` |
| `resource_utilization` | PR #90: расчётная загрузка *по узлам* | workload, явно заданная область применения требования | `not_evaluated`; `target_scope_unspecified` |
| `availability` | Нет модели отказов | MTBF/MTTR, зависимости компонентов, резервирование | `not_evaluated`; `reliability_model_unavailable` |

Если `workload=None`, для трёх зависящих от нагрузки типов
(`latency`, `queue_size_percentile`, `resource_utilization`)
используется `missing_workload`. Незарегистрированный обработчик любого
другого типа получает `no_validator`. Неизвестный внешний
`type_identifier` отклоняется дискриминированным Pydantic-union ещё
при чтении сценария; неизвестный программно добавленный тип также
не должен пройти диспетчер незамеченным.

## Границы и дальнейшая эволюция

Это **отчёт о покрытии проверками**, а не новая оценка производительности.
JSON/PDF и схема v1 из PR #90 не изменяются, вывод
`LATENCY_NOT_EVALUATED` остаётся в отчёте производительности.
Нельзя выводить p99 из средней задержки, доступность из наличия реплик,
а выполнение `resource_utilization` из сравнения с внутренним
порогом насыщения 98%.

Чтобы действительно проверять требования к отдельным компонентам, сначала
понадобится явная модель области действия (`target_node_identifiers`
или scope) и договорённость о том, для какой нагрузки рассчитывается
метрика. Следующий валидатор должен работать с типизированным
показателем, его единицей измерения, методом расчёта и доказательством,
а не угадывать целевой узел по именам или похожести строк.
Внешний отчёт версии 1.0 использует индекс в списке; постоянные ID
потребуют явной миграции контракта сценария.

При отсутствии проверки статус генерации C4 может быть `succeeded`,
одновременно со статусом `incomplete` у отчёта NFR. Это ожидаемое,
а не противоречивое поведение. Проверяющий обязан смотреть оба статуса.
