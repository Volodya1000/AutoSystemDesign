# Краткий план презентации AutoSystemDesign

## Задача

Подготовить материал для системного архитектора Сергея, чтобы за пару минут понять назначение инструмента и перейти к предметному обсуждению. Это не презентация для продажи проекта.

**Формат:** 5 слайдов, 16:9, без отдельного титульного слайда и длинного вступления. На слайде одна мысль, до 3 коротких пунктов. Не дублировать сказанное на соседних слайдах.

## Содержание слайдов

### 1. Что делает инструмент

**AutoSystemDesign строит первый вариант архитектурных артефактов из YAML-сценария.**

Вход: функциональные требования, профиль нагрузки и заданные нефункциональные ограничения.

Выход:
- C4-модель и диаграмма архитектуры;
- Sequence-сценарий для каждого функционального требования;
- REST API, OpenAPI 3.1 и HTML-представление Swagger UI.

Результат предназначен для инженерного ревью, а не для автоматического утверждения архитектуры.

### 2. Пример: сервис сообщений

В демонстрационном сценарии два требования:
- доставить личное сообщение: онлайн через WebSocket, офлайн через очередь и push-уведомление;
- передать отправителю статус прочтения сообщения.

Для одного сценария инструмент формирует архитектуру, сценарии взаимодействия и модель API. Использовать реальные файлы одного запуска, если они подготовлены; не выдумывать результаты.

### 3. Как обеспечивается проверяемость результата

LLM возвращает JSON доменных объектов. Проект разбирает его в типизированные модели, проверяет и только затем генерирует PlantUML обычным кодом. LLM не пишет исходник диаграммы.

Проверки охватывают:
- типы вершин и разрешённые связи, целостность графа и циклы;
- загрузку вычислительных узлов, теоретическую задержку и бюджет;
- ссылки и согласованность в Sequence и API.

При ошибках проект может передать замечания модели и повторить генерацию в пределах заданного числа попыток. Эти проверки выявляют известные нарушения, но не доказывают корректность всей системы.

### 4. Как пользоваться

- Запуск из CLI с YAML-сценарием; параметры генерации и рендеринга задаются в конфигурации.
- LiteLLM вызывает модель через OpenAI-совместимый API; предусмотрен вариант с локальным LM Studio.
- Диаграммы можно рендерить через PlantUML Server в Docker.

В конфигурации по умолчанию используется режим `structured_output_mode: prompt`: схема передаётся в запросе к модели, а результат отдельно разбирается и валидируется. Режим рендеринга `auto` может использовать публичный сервис; для чувствительных данных нужно явно настроить разрешённый endpoint модели и локальный рендерер.

### 5. Ограничения и темы для обсуждения

- Сейчас входом служит YAML. Загрузки произвольных BRD/PDF/DOCX и отдельного GUI нет.
- Наличие типа NFR в модели не означает, что он автоматически проверяется. Например, в текущей композиции не подключена полноценная проверка SLA доступности.
- Генерация требует проверки архитектором; количественные оценки точности и экономии времени не заявляются.

**Для обсуждения:** какие входные требования и выходные артефакты нужны в реальном процессе проектирования, а какие проверки должны быть обязательными до использования результата.

## Требования к оформлению и тексту

Презентация должна выглядеть как спокойный рабочий материал инженера, а не рекламный питч.

- Светлый однотонный фон, тёмный текст, один сдержанный акцентный цвет.
- Простой шрифт, ровная сетка и одинаковое оформление всех слайдов.
- Без стоковых изображений, декоративных иконок, градиентов, 3D, анимации и фоновых узоров.
- Не использовать слоганы, маркетинговые эпитеты, эмоциональные заголовки и неподтверждённые обещания.
- Не писать длинные определения, повторные выводы, общие фразы о «революции ИИ» и очевидные пояснения.
- Оставлять только информацию, нужную архитектору для понимания реализации и обсуждения ограничений.
- Не маскировать недостающий результат иллюстрацией, похожей на скриншот продукта. Использовать только проверенные артефакты.
